# MVP 数据与交通准入根因定位

2026-10-24。仅诊断，未修改业务代码、准入规则、候选包或正式运行库。

## 结论

阻塞由三件事叠加：采集侧仅产出待审候选；规划侧把高强度核验要求作为所有数据的统一门槛；正式服务没有接入高德动态估时的调用链。当前缺少“有来源的参考资料和 Provider 估时可参与 MVP 排程，同时保留不确定性”的使用策略。

此前将 `ready=0` 解释为“不能导入”不准确。维护导入器允许保存未核验候选，`ready` 是另外计算的业务准入状态；正式库为空也包含先前一直未执行正式写入这一流程因素。仅执行导入不会让数据自动成为规划可用资料。

## 本次复现

- 13 个候选包均通过当前维护 CLI 的内存 dry-run；其中 3 个包是空包。每个非空包均为 0 条 ready。包之间存在重叠，不累计为独立采集量。
- 团队工作簿转换包：469 条接收，0 条 ready；旧采集包 188 条、扩展包 112 条、路线 v1 包 17 条、队员回填转换 v2 包 21 条均通过结构与引用校验。
- 上述非空包的每条记录均触发 `UNVERIFIED`、`RIGHTS_NOT_CONFIRMED`、`OUTSIDE_VALIDITY_OR_UNKNOWN`；部分地点另缺坐标。
- 正式库以 `mode=ro` 查询：`city_facts=0`、`city_fact_revisions=0`、`city_engine_operations=0`、`city_engine_routes=0`。
- 纯内存受控输入复现：可用地点仅将来源改为 `internal_only`，地点即不可用；资料有效期覆盖明天完整行程、但从明天才生效，前一天规划仍被拒绝；成功高德报价转换后耗时变为未知。
- 本轮没有新增外部 API 调用，没有运行全套回归；结果属于当前代码路径及本地输入复现。

机器摘要见同目录 `mvp-data-admission-audit-20261024.json`。

## 具体原因

| 原因 | 当前行为与影响 | 代码位置 |
| --- | --- | --- |
| 采集与使用策略未接通 | 候选生成器统一设置 `unverified`、`internal_only`，不提供事实有效期；这类输出天然不满足规划准入 | `collector/validate.py:419` |
| 所有事实共用同一强度门槛 | 地点名称、来源、菜品、供应与营业规则均要求 verified、许可与有效期；verified 又强制核验人、方法、时间和有效起止 | `backend/app/city/facts.py:29`、`:214` |
| 来源链递归放大阻塞 | 来源自身也继承完整事实准入；即便某地点内容足够，其任一引用来源不 ready，地点仍被拒绝；不存在按有效替代来源择优的逻辑 | `backend/app/city/engine/context.py:18` |
| 展示许可与规划使用共用字段 | `internal_only` 不只影响对外展示，还使规划中的事实及依赖失败；公共事实目录更直接过滤掉这类记录 | `backend/app/city/facts.py:220`、`:281` |
| 提前规划与有效期混淆 | `ready` 同时检查评估时刻、行程开始和结束；明天才生效但完全覆盖明天行程的资料，今天也不能用于规划 | `backend/app/city/engine/context.py:29` |

| 正式规划缺少在线交通装配 | 正式 context 只读取事实表与运营表；参考问路独立查询高德，成功结果也不进入规划矩阵。只放开一个枚举条件仍不够 | `backend/app/city/engine/service.py:20`、`agent/reference_routes.py:118` |

## 规则放宽也不会自动消失的缺口

- 地点无可用坐标仍无法请求两点道路路线，需要用高德匹配具体地点；景区中心点与实际出入口须区分。
- 队员已填写第一楼营业与最后接单时间，但上一轮 v2 转换包没有餐馆的营业规则记录；这是转换遗漏。
- v2 将队员提供但未声明坐标系的返程坐标直接标为 GCJ02，并复制到景区及两个入口地点；还把文档文件时间写成观测时间。这些都需要纠正来源含义，不能当作已证实事实使用。
- 夜市回填中的“12:00左右收摊、最晚至2点”存在跨日表达歧义；v2 人为截断到23:59:59属于模型适配处理，不是管理方给出的闭市时刻。
- 旧日期营业规则、节目介绍、目标日场次属于不同数据，不能通过批量换日期解决；营业区间与演出起止等确有冲突时仍应保留冲突。
- 有些采集轮次归档了网页但候选包为0条，说明原始资料还没有完成字段抽取与映射；解除 ready 检查不会生成缺失记录。

## 下一轮修改范围建议

1. 将“入库”“可展示”“可用于参考规划”“已人工核验”分开；允许有来源的团队资料按实际状态参与 MVP，核验人等信息暂作可选，禁止为了通过而伪造 verified。
2. 按数据类型检查必要字段及适用日期；来源用于追溯，不照搬全部地点/营业事实的有效期要求。对内部计算、对外展示和明确禁止使用分别处理。
3. 接通服务端高德查询至规划矩阵，分别表达 Provider 预计耗时、查询时间、规划缓冲及刷新条件；预览、确认与途中重规划保持一致，失败不沿用伪造或零耗时。
4. 免费进入不触发购票确认；仅在确实需要再入园的路线中检查再入园条件。未知营业等缺口允许保留待确认安排，不能输出无依据的保证。
5. 修正队员回填映射，用相同真实资料完成预览、确认和途中修改闭环；合成演示不替代真实数据 MVP。

本轮停在定位结果，待讨论后再修改上述策略。会话属主、版本冲突、用户确认、必选目标保护及已有历史保护不属于本轮数据准入问题。
