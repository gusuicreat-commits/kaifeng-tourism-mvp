## 四个重点问题

### 1. 票价应独立建表

建议另设采集表 `22_ticket_prices`，保留12表中的开放、停止入场、预约、再入园及适用票种规则。价格放在 notes 暂存是合理的原始记录方式，但不能长期靠解析 notes 做预算。

建议字段：`ticket_id`、`place_id`、票种名称、适用人群、销售渠道、币种、金额下限/上限、计价单位、适用时段/权益范围、生效起止、`source_id`、状态、观察时间、核实时间、版本和备注。未知价格保持未知；优惠票、线上价、门市价、日夜票和套票分别记录，不能混成一个“景区价格”。保留原始单位，转换后端时再按人民币分精确归一。

现有引擎 `PlaceCost` 只支持“地点费用上下界＋证据”，不是完整票种模型。采集票价表完成后仍需转换与选择适用票种，不能宣称现有后端已经支持学生票、套票及多日票的全部规则。本轮只提出数据口径，没有新增工作表或迁移数据库。

### 2. 常规节目：身份入13，未注明日期的时间保留为线索

节目名称、介绍等照常作为13表独立记录；无明确日期的常规时间、文字舞台名放13表 notes，保存来源原文。不是把整条节目只塞进备注，也不把常规“09:00”直接生成明天的14表场次。

MVP阶段不必为了结构复杂度再加表。后续若需要自动处理多套常规时间，可以新增“常规排期候选”表，与14正式日期场次严格分开。当前98条节目都没有 stage_place_id，需要成员3补独立舞台地点，不能把整个景区坐标作为舞台位置。

### 3. 14场次：保持明确业务日期，不猜结束时间

一行表示某节目在某舞台、某一天的一次演出。填写依据至少包含：明确日期、节目ID、来源、带时区的开演时间、场次状态和核对时间。对只写“今日”的页面，应有可追溯的当日发布/有效日期依据；仅有浏览或保存日期不足以确认演出日期。

结束时间未知可以作为待核实记录留空，不能默认0或任意加30分钟；缺结束时间不能用于完整衔接可行性认证。模板允许 stage_place_id 暂空，但现有后端场次必须关联独立 stage 地点，进入正式规划前必须补齐。

`session_status` 应表达 scheduled/delayed/cancelled/unknown 等运营状态；是否 verified 由 validation_status 表达，避免把“已核实”混成“已排演”。checked_at 是核对时间，不自动等于 verified_at。

### 4. ID与状态：基本方向正确，导入前需要映射

- 检查10张核心表：主键格式符合本表规则，没有重复主键；所有已填写、受检查的外键均能定位，未发现断链。空的可选外键不是错误引用，但会形成规划就绪缺口。
- 保留 pl_/ent_/prg_/food_/ven_/vf_/src_/chg_ 等稳定ID，不因排序、改名或合并表而重编。不同景区的同名“南大门”不是同一个入口。
- 成员3和成员4新增地点时，应由统一ID登记或分配号段协调；不要让不同成员分别从 pl_000017 起编号。
- 采集表 candidate/pending_review/conflict/stale/expired 等状态可保留。后端事实核验只有 unverified/verified，另有 business_status；不能把这些原始状态全部压成一个候选而丢失冲突、取消与失效原因，更不能直接改成 verified。
- scenic_spot → scenic、GCJ-02 → GCJ02 等需要明确字段映射。food_street 是街区，不应自动映射成一个可以堂食的 restaurant；provider 也不能全部映射为地图供应商。
