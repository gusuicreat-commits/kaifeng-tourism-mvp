# 首条真实路线接入执行方案

版本 v1.0，2026-10-24。目标是把一条有限的开封主城区连续行程从候选资料推进到可被城市规划器采用的事实与交通证据。当前文档记录执行入口、准入门槛和实际缺口，不代表路线已经可执行。

## 选定的第一条链路

2026-10-24 仅为已有候选包的历史业务日期，用于检查导入结构；实际游客游玩日仍需指定并重新核验。以下是待判定可行性的样区与暂定顺序：

开封府夜游 -> 第一楼·中华老字号（寺后街总店） -> 鼓楼夜市 -> 返程点

选择理由：三类活动位于鼓楼主城区候选范围，已有团队工作簿中的统一实体、目标日开放规则候选、餐饮门店坐标候选、菜品供应候选和官方夜市身份来源，可以先验证最小闭环。路线不把搜索摘要、平台推荐菜或一次地图参考问路直接当作正式事实。

顺序必须待营业和转场证据齐备后决定。夜游看完后可能已经超过餐馆接单时间；出现冲突时明确提出调整顺序，不能宣称该顺序已经可行。此样区用于数据接入预验；PRD 的重点景区完整场次及现场 V1 验收仍需另行完成。

## 交通接入门槛

正式规划需要为以下每一段建立受控 Journey/交通证据：

1. 起点到开封府真实入口。
2. 开封府出口到第一楼门店。
3. 第一楼到鼓楼夜市实际入口。
4. 鼓楼夜市到返程点。

每段至少要有起终点、坐标系、交通方式、获取时间、适用时段、估时上下界、路径引用、来源和进出园边界证据。城市地图 API 的一次成功返回只能作为交通估计候选，不能自动变成正式 verified 路段。景区内部从入口到活动场地的通行仍需官方导览或现场走查证据。

## 执行阶段

### A. 事实核验

- 补齐开封府坐标、真实入口、入口方向、目标日夜游规则、预约和再入园条件。
- 补齐第一楼目标日营业时间、最后接单和用餐停留参数；确认门店坐标。
- 用带门店名的当前菜单、商家确认或现场点单记录核验至少一条菜品供应关系。
- 补齐鼓楼夜市目标日位置、开市状态和营业区间。
- 明确返程点和目标日时间窗口。

### B. 事实包整理

- 统一采用 pl_wb_* 命名空间，逐项解决与旧 place_* 候选的同名关系，不静默合并。
- 所有正式记录补 source_ids、rights_status=permitted、validation_status=verified、核验五元组和有效区间。
- 事实变更只生成新版本，先在隔离数据库 dry-run，再通过 scripts/import_city_facts.py --apply 进入运行库。

### C. 交通与路线验收

- 为四段城市转场取得适用交通方式和时段依据。
- 为开封府出入口和必要的园内连接做最小现场走查。
- 在隔离库加载事实和交通资料，运行规划器，确认未知数据不会被填零，必选目标不会被静默删除。
- 完成一次预览、确认和路线版本生成，再执行一次“跳过或加休息后从当前锚点重算”。

### D. 正式发布门槛

只有以下条件同时满足，才允许把这条路线称为真实可执行路线：

- 所有路线节点和依赖事实 ready=true。
- 四段交通均有正式可用的证据和出入口边界。
- 目标日营业、夜游、餐饮营业和供应关系均通过核验。
- 隔离库规划成功，正式库导入 dry-run 与 apply 结果一致。
- 现场走查记录实际到达、实际用时、偏差和途中修改结果。

## 当前可直接执行的任务顺序

1. 先核验开封府入口、坐标和夜游规则；失败则暂停路线，不用餐饮或夜市候选补齐。
2. 再核验第一楼门店营业与供应关系；平台推荐菜只保留候选。
3. 再核验鼓楼夜市目标日状态和实际入口。
4. 最后确定返程点并查询四段交通。
5. 全部通过后生成只包含这条路线依赖事实的正式导入包。
