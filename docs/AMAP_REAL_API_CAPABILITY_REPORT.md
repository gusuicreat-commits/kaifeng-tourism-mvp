# M4.0 高德真实 API 能力验证

日期：2026-10-22。结论：**Web 服务 Key 已配置；城市地点与三种交通接口真实可用；正式行程接入仍为 PARTIAL。**

本轮累计 **20 次真实请求，18 次 HTTP/业务成功、2 次超时**。成功响应均通过 `status=1 / infocode=10000` 核查，不以 HTTP 200 单独判断成功。没有观察到鉴权、权限不足、配额或限流错误；这不证明拥有其他接口权限或无限配额。两轮执行耗时合计约 **107.46 秒**，费用未核实，报告保持 `null`。

用户本轮提供了“Web服务”类型凭据，并授权接入和测试。凭据从截图经本机识别后仅写入 `.env`（0600，已被 `.gitignore` 忽略），没有出现在命令行参数、代码、报告或日志中。没有登录控制台、创建新 Key、充值或购买额外服务。

机器证据见 [amap-real-api-capability.json](reports/amap-real-api-capability.json)。报告只保存诊断和能力判断，不保存原始 POI 列表、地点坐标、POI ID、路线几何、线路名称、具体交通数值或长期矩阵。

## 2. 真实请求过程与异常

首轮11次：v3景区搜索2次、v5景区搜索1次、餐饮周边1次、步行3次、驾车3次、公交1次。9次业务成功；v5搜索和反向步行各有1次超时。超时没有响应业务码，不能据此认定接口无权限或不可用。

补测9次：v5清明上河园、v3开封府各1次，双向步行2次，驾车和公交各1次，餐饮周边1次，景区到餐饮及餐饮到开封府步行各1次。9次全部业务成功。两轮合计20次，已停止继续调用。

首轮每阶段超时配置为5秒；补测显式提高到10秒，仍为零自动重试、低频串行、共享剩余9次预算。`httpx` 的 timeout 对各连接/读取阶段生效，不是整次请求的绝对墙钟上限。不能把少量补测成功解释为网络问题已彻底解决。

- 双向步行：补测两向均成功，距离/耗时相同；程序仍保留方向性，没有由一向推断另一向。
- 驾车策略：首轮对照有差异，证明策略参数确实影响结果；没有现场检验优劣。
- POI ID：首轮驾车对照有差异；本轮没有保存实际终点几何用于事后人工比图，因此入口准确性仍未验收。
- 景区子地点：v3初轮未返回子地点；v5补测返回子地点信息。子地点存在不是开放入口核验。
- 餐饮：存在提供方业务扩展信息；没有把这些字段升级为经核实的营业、菜品供应或价格承诺。
- 公交：总耗时和接驳步行分别解析，不把总时长当纯步行。v5契约注明总耗时含等待，但这不是实时车辆观测；当前解析未确认的费用和几何保持未知。

本轮没有观察到需要额外购买才能完成已测请求的业务错误。其他高级服务、正式上线配额、商业许可及实际账单费用均未核实，也没有申请或购买。

## 3. 引擎联调：真实数值与合成业务条件分开验收

新增 `scripts/amap_snapshot_experiment.py`，复用现有纯 `plan_trip → CP-SAT → 独立校验`，只在内存运行。调用侧把已匹配的景区A、景区B和餐饮候选映射到隔离场景节点；场景消费相应真实请求得到的距离/耗时。

**实验明确使用合成的2030年测试日历、营业规则、停留时长和固定活动时间窗。单次API估时仅作为固定测试常数，绝不是2030年预测、全天可靠上界或已核实营业事实。** 同一节点的零移动只是合成场景设定，没有用直线补真实道路。没有设置未经核实的真实演出场次。

| 检查 | 实际结果 | 解释 |
| --- | --- | --- |
| 步行报价进入CP-SAT | feasible，实际数值被使用 | 只证明数值和接口兼容 |
| 驾车报价进入CP-SAT | feasible，实际数值被使用 | 停车/接驳不在已核验业务范围 |
| 公交报价进入CP-SAT | feasible，实际数值被使用 | 没有认证混合交通的总步行上限 |
| 两个必选访问、固定时间窗及结束要求 | 三种模式均保留并通过校验 | 固定时间窗是测试参数，不是真实演出 |
| 时间不足 | 三种模式均拒绝可行承诺 | 不放宽必选条件 |
| 交通资料缺失 | 三种模式均返回needs_data | 不把未知填零 |
| 纯步行硬上限 | 限制低于所需步行时拒绝 | 仅验证walking模式 |
| 可选餐饮 | 包含餐饮的合成方案feasible | 两段交通数值来自真实API；营业和用餐时长为合成 |

正式准入层 `quote_to_engine_estimate` 保持独立：真实报价不能自动变成核验路径，也不直接填成正式估时上下界。现有正式 `TravelEstimate / Journey` 需要路径、有效期、规划全时段估时依据和出入口证据；这些缺失时仍返回未知，正式试算为 `needs_data`。

因此，本轮可以认定 **数值适配可行**，正式集成评价为 **requires_additional_data**，能力分类为 **PARTIAL**。不能把合成场景的 `feasible` 写成真实游客已可安全执行整条路线。

现有纯引擎不要求数据库，实验没有保存第三方矩阵。但正式候选和路线服务会持久化 `Journey`，其交通耗时、来源、缓存和再展示许可仍需确认。本轮没有绕过这个限制启用正式接入。

## 4. 仍然解决不了什么

- **真实入口**：POI中心和子地点不能单独证明当前开放的入口、检票方向、预约或再次入园条件。入口对照方案A完成坐标算路，C完成驾车POI ID对照；B因缺少人工/官方确认入口未测试。实际终点与入口的几何一致性未验收。
- **园内路线**：城市路线接口不能直接充当完整园内可通行图。需要景区官方数据或逐段核验的内部道路及入口衔接。
- **演出**：仍需明确日期、舞台、起止时间、停止入场和必要缓冲。交通估时只能辅助核算，不能保证赶上。
- **餐饮**：仍需真实商户定位、营业规则和菜单/商家确认的菜品供应；店名含“灌汤包”不是供应证据。
- **客流**：本轮没有历史/实时客流观测，没有热度、人数或排队预测结论。
- **未来交通**：未验证未来时段交通可靠性，单次报价不是全时段保守上界。
- **公交总步行**：现有引擎硬步行预算只统计walking模式，尚未覆盖公交接驳与驾车后的步行。当前不开放这类正式约束承诺。

## 7. 协议边界与正式接入建议

已核对官方[路径规划2.0](https://developer.amap.com/api/webservice/guide/api/newroute)、[POI搜索](https://developer.amap.com/api/webservice/guide/api-advanced/search)、[搜索2.0](https://developer.amap.com/api/webservice/guide/api/newpoisearch)、[错误码](https://developer.amap.com/api/webservice/guide/tools/info)和[服务协议](https://developer.amap.com/pages/terms/)。第3.5、7.3条限制超授权存储/缓存/使用；第3.4条涉及模型或算法训练、数据集构建。能访问接口不等于获准长期保存、导出、训练或二次分发。

正式接入顺序建议：

1. 以已实测的v3地点搜索、v5城市交通报价作为首选候选Provider；v5地点搜索可保留为增强，避免无必要重复查询。
2. 先完成两景区的真实入口、有限通行段及目标日期规则核验，再做小范围现场走查。
3. 明确交通估时有效期、未来时段使用和缓冲策略；缓冲是规划参数，不能称作排队实测或到达保证。
4. 扩展公交/驾车接驳步行的契约和独立校验后，再允许涉及总步行上限的混合交通承诺。
5. 向高德确认ETA/来源随行程保存、缓存期限、路线再展示、比赛展示及商用许可；获得明确边界后再接正式候选确认链。
6. 保留超时、过期、无路线和权限不足降级；不因短期补测成功移除这些处理。

队友优先补：入口/出口坐标和坐标系、名称及方向、核验日期来源、入园和再入园规则、园内道路、日期化演出场次、餐饮营业及菜品供应、停车/接驳依据。客流缺失继续保持未知。

**最终判断：高德已证明能成为汴梁游记城市地点与交通估时的数据来源；它单独不足以支撑正式可执行的完整旅游行程。现阶段可确认接口和数值适配可行，正式上线仍取决于入口、业务事实、估时策略、混合交通步行统计和数据使用许可。**
