## 助手延续素材与逐项补问

移除独立“用素材篮规划”开关和整张规划条件表。无正式路线且已有素材时，助手自动显示本次所选名称，沿用当前行程或已保存的规划条件，每次只显示仍缺的一组问题（日期、时段、出发地点、返程地点）。从素材篮进入也使用同一流程；详情提问继续围绕该对象，不强制展开规划。

日期、时段可以通过聊天回答，也可以用当前问题的控件选择。聊天统一经过已有后端任务及 LLM 需求理解层，返回带原文依据的结构化条件，再由 workflow 合并已保存条件、补问和核验。前端不再按语序匹配规划句子。个人条件仍通过已有 exploration preview 保存，刷新按服务端条件续接。未增加 Agent、求解器或本地权威副本。交通方式和节奏显示在已提供条件中，可点开调整。

已知条件不重复展示空表单；条件标签可回到对应问题修改。候选、失效检测、冲突取舍和最终确认仍调用原接口；自然语言同意不会直接提交路线。普通对话产生待确认候选时，暂时隐藏规划卡，避免两份候选同时展示。移除第 0 版、重复返回条及底部工程入口；手机输入区给小汴梁留出位置，避免遮住发送按钮。

验证使用隔离测试库和合成业务资料，不调用付费模型、不导入运行库。覆盖逐项保存及刷新、一次回答多项条件、非法时段不保存、普通对话、冲突协商、修改后候选失效、确认与取消，以及语音文字进入同一输入框而不自动发送。手机实页为465×769，原万岁山素材保留。

## 统一需求理解与规划衔接（替代前端语句匹配修复）

原先前端按当前问题匹配文字，第一次局部修复又引入 `planningMessage.ts`；因此“我想明天去开封玩”能识别，换成“我明天想去开封玩”仍落入后端修改行程兜底。原 LLM Schema 也没有初始规划字段。前端局部用例通过不能说明需求理解已经接通。本轮移除该文件及对应前端句式测试，将验证移到实际后端解析和浏览器整条链路。

`Understanding` 增加可选 `planning`：旅行城市、原文日期表达、明确起止时刻、起终点名称、节奏、目标、交通方式、预算及素材取舍均携带 quote。沿用现有 Kimi provider、调度、超时及任务 start/step/cancel；没有新建模型服务或 Agent。原文引用、日历日期、时刻和预算由服务端验证；具体地点匹配许可事实，旅行城市不当成导航地点。模型失败、矛盾值、未明确的附加要求均先补问，不用部分规则结果执行修改。

`planning` 分支只提出已校验的 workflow 输入，不提交路线。前端将其交给现有 `BasketPlanning`，携带旅行、素材篮及规划版本调用原 preview/answer 接口。改日期保留原时段并重新核验，旧候选仍由服务端版本检查拒绝。素材降级继续核验原文明确同意和已安排锁定规则。“就这样”只推进或补问，有候选时指向既有确认按钮；不能口头自动提交。无模型时保留控件及裸日期/明确时段等有限输入，不把它们冒充 LLM 理解。具体地点资料不足仍显示待添加。

验证：后端相关 98 项、详情/素材篮与行程浏览器 17 项（分批）、原 Agent 浏览器 7 项通过；生产构建和契约生成检查通过，原 80 条离线语料回归仍通过。覆盖不同语序、无素材首次输入、条件保存及刷新、同日时间保留、无效值/未知地点不写入、查询和否定、附加要求不部分执行、模型故障、取消、素材降级同意、候选失效与确认/放弃。结构化结果携带并核对 trip_id，新增相同版本下的跨旅程防串写浏览器用例；补上该保护后重跑 26 项后端规划用例及 3 项关键浏览器用例通过。浏览器使用隔离库与显式模拟模型响应；[465×769 手机截图](../../screenshots/planning-message-fixed-mobile.png) 已人工检查。

真实 Kimi 共发出两次请求，每次单请求上限、无自动重试，仅发送固定测试句和经联网前断言的临时空白上下文。第一次识别日期但把开封当返程地点，记录在[首次报告](../../reports/planning-language-live-20261022-initial.json)；据此区分城市范围和具体起终点，增加回归。第二次真实解析及原 preview 保存明天日期通过，正式状态不变，见[修复后报告](../../reports/planning-language-live-20261022.json)。可用 `scripts/verify_planning_language.py --check-only --output /tmp/planning-check.json` 离线核查外发内容；显式 `--live` 才允许一次模型请求。运行库未导入测试资料，用户素材与正式行程未修改。已核对当前 5177 正在提供统一后端解析的新前端代码、8017 模型已配置且开发服务已重载。本次只证明上述软件和单条真实解析联调，不代表任意自然语言、真实开封路线或游客效果已验收。


## 地点名称收集与“我的”入口去重（2026-10-23）

无地点目录时，助手直接询问“从哪里出发，最后返回哪里？”，提供两个名称输入框。名称通过原有 exploration workspace 保存，刷新可续接；已知地点仍用原选择框。新增 origin_text / destination_text 仅为游客意向，最长120字，绝不作为事实 ID 或传给路线引擎。聊天中的未匹配地点也可以进入同一条件工作区；匹配前返回 ENDPOINT_MATCH_PENDING，不生成候选路线。对话上下文区分尚未告知的名称与产品仍缺的地图事实，已保存名称不重复询问。

“我的”移除重复的当前行程页签及空状态，保留收藏和设置。底部“行程”作为当前安排的统一入口；非当前且已有日期/站点的记录与旧园内路线按需显示在折叠的“往期行程”中，原数据未删除。

验证：70项后端用例分批通过，覆盖意向保存、取消/版本、权限删除、未知名称不进入求解器、已知地点规划以及连续对话上下文；4项浏览器用例通过，覆盖465×769地点输入、刷新恢复、既有选择框与“我的”导航及往期记录。生产构建、引擎契约检查通过。浏览器使用隔离库和模拟模型；未发送新的付费模型请求或导入运行库事实，不代表未知地点已定位。
