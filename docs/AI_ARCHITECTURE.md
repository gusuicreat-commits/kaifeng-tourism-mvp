## 1 产品目标与最小实现

产品服务开封城市自由行。两大景区是重点验证场景，城市美食和夜游接续属于 V1。首版限定单日、有限核验地点、至少一种有时间依据的交通方式；先完成一条含景区演出、餐饮、城市地点和途中修改的真实闭环，再扩大范围。

优化首先满足用户明确指定的体验与可执行条件，再改善时间、步行和节奏。缺少客流时关闭客流优化，核心行程仍工作。缺少道路、场次时长或转场时间时，对受影响部分标记待确认，不能认证全程可行。

保留 Vue 3、TypeScript、FastAPI、Pydantic、SQLite、NetworkX 和 OR-Tools。现阶段无须为城市级定位迁移数据库或引入多智能体平台。数据库扩展与适配层应与既有模块隔离，按可验证的功能增量推进。

## 2 模块职责与控制权

M1 需求与交互适配：地图点选、卡片、行程编辑和自然语言均生成同一种结构化修改请求。自然语言只提取明确字段、匹配候选实体并解释结果，不自行创造地点、时间或路径。

M2 事实与来源服务：管理统一地点、入口、场次、商户、营业与入园规则，保留来源、有效期、核验状态和版本。先用结构化查询；向量检索不是 V1 依赖。

M3 可选客流服务：复用现有观测和历史统计接口；无数据返回未知，不阻塞行程。游客反馈只作为有时间戳的报告，不能直接成为真实人数或道路通行速度。

M4 行程规划服务：城市转场适配器提供场景间耗时，园内求解器提供真实路段和场次安排，城市协调器联合比较候选并检查全局时间。不能先固定园内最优路线，再机械追加晚餐。

M5 独立校验与说明：复核实体、每段可通行性、时间、营业、出入口、硬目标与来源；结构化输出由后端生成，LLM 仅解释通过校验的结果。

M6 变更与提醒：接受用户手动修改或可信日期变更，重算剩余行程。取消提示依赖真实变更来源；V1 支持前台刷新和手动确认，不承诺后台实时推送。

M7 行程状态：管理当前城市行程、活动进度、位置锚点、候选变更、版本、授权与删除。聊天摘要只是辅助上下文，权威事实来自结构化状态和重新查询的数据。

固定执行顺序为读取状态与版本、归一化修改、查询事实、生成转场与园内候选、联合求解、独立复核、按确认规则提交、展示。所有写入由服务端控制；工具白名单不授予 LLM SQL 或直接提交权限。

## 3 城市行程与数据结构

下列名称是逻辑模型，不是已存在的表或可调用 API。

CityTrip 包含城市、业务日期、开始与结束时间、起终点、偏好、锁定目标、当前活动、状态、version 和 route_version。城市级 ID 贯穿园内外，scenic_id 改为活动或段的可选归属。

Stop 表示一次具体活动，包含 stop_id、place_id、kind、session_id、到达与离开、停留、必选或可选、完成状态与来源引用。同一地点的不同场次用不同 stop_id 表示，允许重复到访但禁止不合理重叠。

Leg 连接两项活动，包含交通方式、起终端点、出发与估计到达、耗时及不确定范围、geometry 或外部导航入口、数据来源、获取时刻、有效期、坐标系和核验状态。路线缺失不得以直线或零分钟代替。

PositionAnchor 记录游客明确确认的地点及时间。V1 优先使用已知 place_id 或路网节点；设备定位是后续可选输入，需要精度、坐标和时效检查。默认不保存连续轨迹或将精确定位送入聊天上下文。

Place 区分城市景点、景区、园内点、入口、餐饮和夜游地点。Dish 表示菜品兴趣，不等同商户。餐饮点必须能定位并关联营业依据，菜品与商户关系也需核实。

Evidence 保存来源、发布与采集时间、有效日期、核验方法、版本及冲突状态。已核验事实、估计、用户反馈、模拟和未知分别标识，不能只靠一个 is_simulated 字段表达可靠性。

## 4 园内外路线与时间计算

园外优先接成熟路径服务，适配器负责凭证、请求模式、坐标转换、限额与失败处理。浏览器地图搜索或跳转导航只能帮助用户查看位置，不会自动向后端返回交通时间矩阵。选定服务并完成真实调用核验后，才算接通。

首版小范围步行可使用有起终点、采集时间和走查证据的人工耗时作为明确标注的替代；数据不足时只输出待核算安排。未来驾车或公交必须处理相应等待和换乘，不能复用步行系数。

园内继续使用 NetworkX 求段路径，OR-Tools 排活动与时间窗；只在经过核验的连通子图内提供正式路径。场景转换必须经过真实对应的入口或出口，计入进出园耗时与票务规则。再入园未知时不自动设计离园后返回。

最晚到场时间为场地停止入场时刻与开演减缓冲的较早值；已核验停止入场时刻缺失时使用明确标注的规划缓冲。预计到达为上一活动结束加转场及入场转换。时间余量等于最晚到场减预计到达。

缓冲属于参数，候场属于计划等待，排队属于现场过程，三者分开。没有结束时间的节目不能默认瞬时结束。交通存在区间时使用保守端点复核并保留区间；单值估时仍标为估计，不推导保证。

城市协调器先枚举有限的场景顺序、入口和时间预算候选，再调用园内求解器；若晚餐或末班返程冲突，应改变分配重算。该方法只在候选集合内寻优，不能宣称全城全局最优。具体模型与边界见 ALGORITHMS.md。

## 5 变更提交与连续执行

首次规划保存一份明确确认的需求。游玩开始后，重规划输入包括当前时间、可靠起点、已完成活动、跳过活动、仍锁定的目标和剩余预算；只计算未完成部分，不把游客重新放回景区入口。

自然语言先生成候选；游客确认后重新查询事实并求解。明确的加餐、休息、移动可选活动等按钮可以表达直接修改意图，但若影响锁定目标，必须展示影响并确认。没有副作用的导航和查看操作不增加确认步骤。

求解在事务外进行，提交时再次校验属主、行程版本和依赖事实版本。版本变化则拒绝旧候选；成功后以一个事务提交新路线、时间、状态和事件。失败保留上一结果，同时标出其中已过期或取消的部分。

场次取消、过期或营业变化使受影响安排失效。系统可以先计算替代候选；未获确认不得移除必看目标。可靠变更未接入时只允许显示最新核对时间并由用户刷新，不宣称自动监测。

外部导航返回后按同一 CityTrip 恢复；地图、卡片、提醒引用同一 route_version。旧版单景区 trip 由兼容层明确读取或迁移为单段行程，不按名字自动拼接成城市行程。

## 6 接口边界与迁移方案

现有 /api/plans 和 /api/v1/trips 契约仍服务单景区；本次文档更新未改变任何运行接口。新 CityTrip 契约先形成 schema 与契约测试，再选择独立版本命名空间上线，禁止让旧客户端无提示接受不同语义。

新增逻辑操作包括 create_city_trip、get_city_trip、propose_change、confirm_change、replan_remaining 和 set_position_anchor。写请求包含 request_id、expected_version、城市行程 ID、类型受限的操作及参数；服务端决定 owner。具体路由由实现时的契约文档确定，本文名称不是可调用接口。

返回中必须有新版本、活动与转场、整体及逐段可行性、证据状态、冲突清单和未满足目标。候选响应与已提交响应不同；不能把候选显示为已更新。

M7 的会话授权、滑动过期、幂等、并发保护、有界上下文和独立删除台账全部复用，并扩展到城市行程、活动、转场缓存引用和候选。不能通过增表绕过导出与删除。账号和长期偏好仍待真实身份适配。

SQLite 可以支撑有限原型。迁移采用增量 schema、版本化读取和可回退适配；先在副本验证旧数据、并发和删除台账，再接运行库。无需因“城市级”三个字先换数据库。细节见 M7_MEMORY.md。

## 7 任务驱动地图与降级

视觉采用宋风浅立体，路线、按钮、节目时间保持清晰。探索时突出景点和餐饮；执行时突出当前锚点、下一站与路径；赶演出时突出到场要求和时间余量。复杂整图时间轴、满屏热力与无数据卡片不是首版重点。

无定位时手动选已知地点；定位质量不足时不自动吸附到另一条路。示意地图明确标识，不能用于真实位置匹配。城市与园内地图切换只改变视图，不创建新行程。

无 LLM 时，点选、结构化修改、规划和模板说明继续可用。无客流时关闭拥挤目标。无交通服务或场次关键字段时输出待确认部分；无真实道路时只提供目的地或示意导览。

时间风险标签采用“有余量、紧张、冲突、待确认”，其阈值属于待现场校准的产品参数。不能把红色时间风险标成拥挤，也不能将剩余五分钟解释为只需排队五分钟。

V1 提醒限定前台会话，触发条件包括下一场临近、硬约束冲突、确认过的数据变更和用户主动操作。刷新后的过期提醒按版本失效；用户跳过或结束行程后停止对应提醒。

## 8 实施顺序与验收

第一步是选定有限场景，核对路线、入口、节目开始与结束、餐饮位置营业和城市转场，完成数据状态登记。已有采集包仅为候选事实，不等于已经接入运行库。

第二步建立 CityTrip、Stop、Leg 和版本化操作契约，扩展 M7。第三步接城市转场与园内适配，加入缓冲、用餐、进出园及全程复核。第四步完成直接操作、行中起点和剩余行程重算。第五步做任务地图、失败降级与现场走查。

V1 的两个工程里程碑分别为基础导览时间判断、城市跨场景闭环；第二项必做。V2 扩展受约束语言服务与可信变更，V3 再扩大覆盖及数据驱动拥挤能力。原十天排期仅为历史记录，新的日期应按数据准备度与工作估算确定。

工程验收要求规定场景中无硬约束静默违约、无模拟冒充真实、无越权访问或失败覆盖；这些是待执行门槛，不是当前成绩。现场验收记录真实路径和到达偏差；游客实验对比普通导览、地图和美食工具组合。

研究重点是规划耗时、按时到场、无效绕行、修改耗时、跨场景完成、操作步骤与满意度。统一任务与数据条件，记录样本、失败与不确定性。不能用求解器最优值或模拟测试替代真实体验改善证据。
