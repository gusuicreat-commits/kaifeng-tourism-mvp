# 小汴梁统一 Agent 与规划工作流方案

2026-10-24 · 设计提案 v1.1 · 部分实施。本版增加可扩展查询接口与 Provider 注册表。本文描述目标与改造次序，已实施范围在文末单列；不代表整份方案已经完成。

## 1. 设计结论

采用一个语义 Agent、一个服务端编排入口、一份旅行需求视图、一套既有确定性规划引擎。聊天、搜索和规划是同一轮交互可组合的工作，不再成为彼此隔离的产品分支。

主链：用户输入 → 加载旅行上下文 → 统一语义理解 → 服务端验证并合并意向 → 按需调用逻辑工具 → Provider 注册表选择 API 适配器 → 结果标准化与事实准入 → 既有规划 workflow / CP-SAT → 结构化结果与解释 → 用户确认 → 原引擎提交正式路线。

查询能力与供应商分开：workflow 只依赖稳定能力名，同一能力可以接入多个 API。新增同类 Provider 只增加适配器与注册配置；新增业务能力才扩展对应契约。初版用模块内注册表和配置完成，不引入插件平台或额外服务。

普通聊天在回答后结束；资料查询在结果后结束；只有需要正式安排行程的请求才进入规划。不是每条消息都完整跑一遍规划链。

保留模块化单体、现有模型Provider、调度器、M7、事实服务、素材篮和CP-SAT。不新增多Agent、Agent框架、向量库、第二个求解器或独立后台任务系统。

## 2. 当前代码与本方案的关系

本轮复核 `agent/service.py`、`understand.py`、`models.py`、`conversation.py`、`planning_intent.py`、`toolbelt.py`、`exploration.py`、`travel_services.py`、`engine/service.py`、`CityAgentChat.vue`、`BasketPlanning.vue`。

已复现截图问题：未知句子默认成 modify → grounded 在模型前拒绝问句 → clarify。原文“你能查阅相关酒店资料吗”调用模型0次。另一个反例“你能帮我找酒店吗”被酒店关键词旁路直接当成搜索并写入工作区。隔离记录见 [语义分流诊断](reports/semantic-routing-diagnosis-20261024.json)。其中模型固定输出仅用于证明调用是否到达模型，不能据此评价自然语义准确率。

当前只有一套城市CP-SAT核心；多个接口主要是兼容、不同输入适配和不同确认入口，不能误称已有多个求解器。问题在语义前置规则、酒店旁路、分散需求和前端接力编排，而不是算法核心需要重写。

| 当前 | 改造目标 |
| --- | --- |
| 酒店关键词命中就执行；普通问句可能先被当修改校验 | 所有自由文本先进入同一个语义协议；修改证据校验仅用于实际写操作 |
| conversation与业务动作整体互斥 | 一轮可回答问题、提出只读查询及规划变更；每个动作独立校验，解释文字不授予写权限 |
| 酒店需求与exploration需求分别合并 | 单一需求归并服务管理作用域与冲突；各类存储保留清晰职责 |
| planning结果返回前端，再由组件触发业务请求 | 后端完成规划编排，前端只显示、填表和传递明确选择 |
| 工具循环后多为固定结束文案 | 一个结果协议提供回答、卡片、缺项、约束覆盖与候选差异；解释基于工具证据 |
| V2/V3及素材篮各自承担部分流程 | 当前V3任务入口收敛为主编排；原接口逐步成为复用同一服务的薄适配器 |

## 3. 职责划分

### 语义 Agent

理解用户在询问什么、想查什么、想新增/修改哪些条件，解析明确原文、指代和硬/软要求；给出必要的查询建议与回复要点。可以组合“先解释早餐，再查200元内酒店，再尝试排进旅行”。不能直接执行SQL、写事实、调用确认或决定真实路线可行性。

不把“吗/能不能/如何”统一等同于禁止执行：能力询问、间接请求、操作教程、条件假设分别理解。无法消歧时可回答能力并询问关键项，不用“请明确修改”替代一切。用户引用的酒店宣传、网页文本不能成为用户授权。

### 服务端 workflow / orchestrator

是唯一执行总控。接收语义结果，验证动作、合并需求、计算必需缺项、确定工具依赖、执行获准查询、评估证据是否够用、调用已有引擎、组织结构化结果。保存任务状态、处理取消、版本冲突、幂等、超时和失败。

Agent可以建议查询，服务端按已校验需求生成执行计划。常见任务使用固定依赖流程；初版不对每个确定步骤再问一次LLM。复杂任务的受限探索保留为后续按收益启用的策略，不另起一套Agent。

### 工具与 Provider

分三层，避免把 FlyAI 或高德写进语义协议和规划流程：

| 层 | 职责与接口 |
| --- | --- |
| 逻辑工具层 | `search_hotels`、`search_merchants`、`search_parking`、`get_routes`、`get_weather`；只接收已校验的业务参数 |
| Provider 注册表 | 按能力、授权、适用范围、时效要求、业务优先级和健康状态选择适配器；安排预算内的备用查询 |
| API 适配器 | 负责具体供应商的认证、参数转换、调用与标准化；原始 JSON 和供应商错误文本不传播到业务层 |

已有 FlyAI 酒店、高德 POI/参考交通和本地事实入口逐步包装成适配器；未来 OTA、天气、交通或其它授权 API 在这里注册。天气等尚不可用能力只保留接口定义，不宣称已接通。酒店搜索、详情、房型和评价分别声明支持情况，不能因支持搜索就自动开放全部酒店能力。

注册项建议包含 `provider_id`、`adapter`、`capabilities`、`supported_scopes`、`field_coverage`、`credential_ref`、`priority`、`timeout_ms`、限流与缓存策略。`credential_ref` 仅引用服务端环境变量；密钥不进入前端、Agent prompt、日志、文档或 Git。实际能力清单从配置和授权状态生成，模型不能指定任意 API 地址或自行创建 Provider。

初版按“可调用且满足范围 → 配置优先级 → 预算内尝试备用”执行即可，不新增 LLM 选 API 或复杂评分系统。`enabled / disabled` 表示配置；`unauthorized / unavailable / rate_limited / degraded` 表示可调用性；`stale` 表示某份结果过期。禁用、无授权或范围不匹配的适配器在调用前排除。

统一请求包含 `capability`、业务参数、`request_id`、旅行/需求版本、截止时间与时效要求；重试、备用接口和依赖查询共用本轮预算，不重置倒计时。只读 Provider 在白名单内执行；下单、支付等写接口不属于本次扩展。

统一结果包含 `schema_version`、`provider_id`、`capability`、`source`、`checked_at`、`valid_until`、`scope`、`evidence_status`、`limitations`、`error_code` 与类型化 `data`。不同能力使用酒店、商家、停车、路线或天气各自的结果模型；来源、时间与范围必要时细化到字段，不能给整条对象贴一个“已核实”就覆盖未知设施。原有事实准入规则决定结果用途，供应商成功回包不自动等于正式事实。

超时、限流、权限不足按错误类别返回；仅在同能力、授权和范围适合且预算足够时尝试备用 Provider。没有备用就报告该项不可用，其他独立查询继续。成功但无匹配结果不冒充服务故障。不同来源的对象ID必须带供应商命名空间，经身份核对后才能关联；报价、房型、日期或坐标系不同的记录不能直接拼接。冲突保留双方证据，不把重复来源投票成事实，也不静默用较弱证据替代较强证据。

缓存按能力、标准化参数、Provider、证据范围和必要的旅行/授权作用域隔离；保存与复用遵守接口许可和有效期。迟到、取消或旧需求版本的结果不能覆盖当前候选；过期结果可带标记供参考，不能沿用其正式准入资格。`execution.provider_trace` 保留本轮尝试与备用原因，供解释与调试使用；前端默认只展示来源、更新时间及影响，技术追踪按需展开。

新增同类 API 的固定接入步骤：实现现有能力契约 → 配置服务端凭据引用 → 注册支持范围和策略 → 通过标准化/故障/证据验收 → 启用。无需修改 Agent schema、engine 或前端主流程。若 API 提供全新业务能力，则显式新增能力契约与展示映射，仍复用同一编排入口。

### engine 与提交

复用现有CP-SAT、独立复核、剩余行程保护和确认事务。只有engine证明可行的方案才成为可确认正式路线。用户确认再重查版本、事实指纹、进度与有效期；兼容确认接口最终委托该提交服务。聊天文本“好的”不自动提交路线。

### 前端

呈现聊天、候选、地图、预算及时间轴；发送用户输入、表单补充、候选选择和明确确认事件。所有入口走相同需求归并与规划服务。表单和按钮不必为了统一而额外调用LLM；前端不再承担“收到planning_action后继续推动另一个工作流”的总控职责。

## 4. 统一语义协议

建议将 `Understanding` 演进为单个 `TurnIntent`，第一版只包含：

- `questions`：用户要回答的能力/概念/稳定知识问题，指明是否需要外部依据。
- `requests`：只读查询、首次规划、修改规划、进度报告、取消等类型化请求，可同时出现。
- `requirement_patches`：字段、作用域、值、硬/软、原文证据与修改方式；未提及字段不补猜。
- `references`：指向服务端已给出的候选ID或用户原文地名；无法唯一消歧时保留未解析。
- `ambiguities`：真正影响执行的歧义与关联请求，不是一段泛化拒绝文案。

协议不含最终事实断言或可执行代码。回复由回答要点、服务端工具结果及业务结果共同形成。模型的“写完了”“已经订好”不能替代回执。

仅当 `requirement_patches` 或业务操作将改变意向/正式状态时运行相应写入证据门；普通聊天不通过修改授权门。Schema只禁止危险字段组合，不禁止合法的“解释 + 只读查询”。

保留输入长度、结构、字段值及原文校验；解析失败不应用部分patch，不触发工具，用“这段话我还没理解完整”并保留已知条件。若结构化部分有效但存在独立未支持请求，可回答和执行明确部分，同时列出未处理项，不声称整轮已经完成。

## 5. 统一旅行上下文

“统一”指一个读取视图和一个需求归并入口，不把聊天、实时价格和正式路线混进一张JSON。

| 分区 | 权威来源与生命周期 |
| --- | --- |
| 当前对话 | 同旅行最近消息、上一轮实际执行摘要；不是事实或授权 |
| 本次需求 | 日期范围、人数房数、预算、住宿/餐饮/交通偏好、目标和锁定项；每个字段带来源与作用域 |
| 事实与查询快照 | 原事实目录和Provider缓存；带provider_id、capability、来源、对象范围、时效与证据等级；到期重新查；执行摘要关联provider_trace |
| 待确认候选 | 查询条件指纹、需求版本、正式路线版本、有效期及差异；不可覆盖正式版本 |
| 正式行程 | 原engine路线、进度和锁定项；独立版本，提交后才改变 |

本次需求示例：`trip.total_budget_fen=100000` 与 `lodging.nightly_cap_fen=20000`分别保存；`lodging.window=hard`不能因“最好便宜些”被删除；日期改变使关联报价、场次与路线预览失效，但不删除这些需求。

弱偏好不能覆盖已有硬要求。修改硬要求需要本轮明确授权；有歧义先提出变更，不实际放宽。已完成活动不被需求patch重写，锁定活动的影响在预览中单列。

酒店选择保存的是 `selected_hotel_intent`；除非地点、入口、入住时段和交通通过正式准入，否则它不能成为引擎起点。未核实菜品供应的餐厅同理。

迁移时先聚合现有draft、basket、exploration、services、route；对冲突保留双方并要求取舍，不按“最后写入者”覆盖。随后把需求写入收敛到一个归并服务，其余表保留候选缓存、事实、路线等职责。快照记录各自版本，暂不需要全库改表或复制全量事实。

账号与长期偏好沿用当前边界：未有认证账号时只承诺本会话/本旅行，不伪称跨设备长期记忆。

## 6. 编排流程与效率

1. 授权、限流、读取同一旅行状态快照和实际能力清单。
2. 自由文本调用一次语义模型。明确按钮/表单直接产生类型化事件，跳过LLM但使用相同校验。
3. 分动作校验；纯问答直接答。明确的本次旅行条件可按版本保存为意向；重要取舍先提出patch，正式路线始终另行确认。
4. 依请求判断必需字段。酒店查询只需要其查询所需日期等，不要求先补完整景点/返程资料。只询问用户缺的信息；产品缺数据直接说明。
5. 服务端生成逻辑查询计划，再由注册表选择各能力的 Provider。独立查询在共享截止时间与限流允许时并发；依赖酒店选择的周边停车与路线后执行，不根据酒店未确认坐标猜入口。备用查询只在预算与策略允许时执行，不额外调用模型选供应商。
6. 适配器输出类型化结果，按来源、时效、对象与字段范围归并；重复对象需身份核对，冲突保留。硬要求未知只能列为“待核实候选”，不能计为已满足；单项失败不抹掉其它成功查询。
7. 请求规划时将需求和准入事实交给现有exploration/engine。缺资料时保留查询成果、需求与旧正式路线，明确指出不能确认的部分。
8. 用同一结果协议返回回答、卡片、缺项、约束满足表和预览。默认确定性组织回复；必要且预算允许时才追加一次有证据约束的语言表达，不让模型改写数值和状态。
9. 用户明确确认，原engine执行唯一正式提交，前端读取同一最新路线。

复用当前45秒产品任务预算与调度器。一般对话1次LLM；常见查询/规划1次理解，工具后语言表达为可选第2次。不能保证在现有供应商限流下每轮都有第2次调用；许可不足时直接返回结构化结果，不为润色等待。工具超时和余量必须计入同一截止时间，不是每步重置45秒。

初版新编排不启动自由多轮ReAct。既有餐饮探索逐步映射为带依赖的执行计划；查询次数、候选数量和Provider并发均受上限控制。只有真实任务证明固定流程不足，才评估局部额外模型决策，并使用同一执行器、同一上下文、同一预算。

保留 `start/step/get/cancel` 传输方式与前端进度展示；将每个step内的业务责任收敛到后端编排。现有进程内任务15分钟TTL的恢复限制如实保留，暂不引入持久任务基础设施。重启后临时任务可重新请求，正式状态与持久需求从原服务读取。

## 7. 对用户的结果协议

建议 `TurnResult` 包含：`reply`、`cards`、`questions`、`requirements_summary`、`coverage`、`issues`、`preview`、`actions`、`execution`。

- `coverage`逐项返回 `satisfied / violated / unknown / not_evaluated`、证据引用和适用范围；硬窗户未知时不显示“已满足全部要求”。
- `issues`区分 `user_input_missing / product_data_missing / provider_unavailable / unsupported / conflict / stale`。明确每个问题影响哪些请求。
- `preview`区分 `candidate_intent`、`reference_draft`、`formal_route`。不把资料不齐的草稿装进正式确认按钮。
- `execution.provider_trace[]`记录各次尝试的 `capability`、`provider_id`、`provider_status`、`error_code`、`fallback_reason`、`evidence_scope`、耗时及采用结果引用；明确区分因禁用/无授权跳过与真正发起调用。用户追问“为什么失败”时依据摘要回答，不凭历史聊天编造“资料没调出来”。不记录认证头或完整敏感请求。
- `actions`来自服务端白名单，可包含补日期、重新查询、选择候选、查看来源、打开详情、预览或确认；不能由模型创建任意URL或确认权限。

最终路线确认仅对应 `formal_route` 且通过独立验证的候选。保存酒店意向、收藏、标记完成等动作保持各自明确语义，不为所有动作强行套同一个“确认方案”。

稳定知识/文化介绍可以自然解释，并与实时业务事实区分。涉及实时价格、路线、营业、可订、场次和具体设施时必须有查询证据；专业或需要精确引用的知识问题在没有相应检索工具时说明资料边界。本轮不新增开放网络爬取能力。

## 8. 场景的目标表现

| 输入 | 目标行为 |
| --- | --- |
| 你能查阅相关酒店资料吗 | 先说明实际可查字段与缺证边界，再问入住/退房；不执行修改，不强制进规划 |
| 查明天开封200元内酒店，住一晚，必须有窗 | 一次理解中文日期/晚数，查真实候选；窗未知逐项标记，不能当匹配套餐 |
| 早餐是否包含是什么意思？顺便查酒店 | 回答概念并处理查询；缺日期只阻断酒店查询，不丢掉概念回答 |
| 明天两人自驾玩开封，想去两景区，总预算1000 | 合并旅行条件与目标，补必要缺项，查所需事实；有正式证据才求解，否则返回缺口与已完成查询 |
| 酒店换成200元以内，窗户要求不变 | 保留其他条件，查新候选，展示变更影响；资料足够时重新求解，确认前旧路线不动 |
| 取消刚才的修改；这个景点为什么有名 | 取消候选操作与知识问答同轮完成；不删除正式行程 |
| 我已经逛完第一站，再加一顿饭 | 明确记录用户报告的进度，保护历史及锁定项；从有效锚点规划剩余部分 |
| 飞猪超时且无可用备用，但本地场次与地图可用 | 酒店查询单项失败，其余可用工作继续；最终不声称住宿或总预算已核实 |
| 飞猪超时，另一酒店API已启用且覆盖相同查询 | 预算内尝试备用接口，保留来源与失败原因；逐字段核对条件，不静默降低证据要求 |
| 后续接入另一天气或酒店API | 实现能力适配器并注册；原聊天与规划主链继续复用；全新能力另补契约 |

多晚住宿是另一个数据/算法里程碑：可以先理解与检索多晚需求，完整正式多日规划仍需按天起终点、入住/退房时段、住宿成本和跨日依赖模型。后续优先用原同日CP-SAT作为每日求解核心，外层用有界候选协调多天锚点与总预算，不能把每日独立可行等同于整趟可行。首轮统一编排不承诺解决该缺口。

## 9. 文件级改造边界

尽量在现有模块内收敛职责；仅新增小型契约与编排/需求聚合边界，不拆成十几个服务。

| 模块 | 处理 |
| --- | --- |
| `agent/models.py`、`understand.py`、`evidence.py` | 统一TurnIntent；去除未知默认modify与模型前一刀切问句拦截；保留分动作写证据与字段检查 |
| `agent/service.py` | 保留任务生命周期，委托单一编排；移除酒店关键词直接执行；吸收planning前端接力 |
| `agent/conversation.py`、`assistant/context.py` | 聚合上下文、实际工具能力和上一轮执行摘要；控制注入长度，不塞全量事实 |
| `travel_services.py`、`hotels.py`、现有高德适配器 | 保留候选操作及供应商调用，包装为能力适配器；条件合并回统一层，供应商选择回注册表；去除正文关键词解析作为执行入口 |
| 建议新增 `city/providers/contracts.py`、`registry.py`、`normalizers.py` | 定义能力请求/结果、模块内注册与选择、证据标准化；复用现有调用代码，按复杂度拆分，不另设网络服务；与 `agent/provider.py` 的模型Provider职责分开 |
| `planning_intent.py`、`toolbelt.py`、`exploration.py` | 提取可直接调用的业务服务，复用同一需求快照、engine输入与预览；HTTP接口只是适配 |
| `engine/`、M7、`model_schedule.py` | 核心复用；在必要边界加版本字段，不改弱正式准入和提交约束 |
| `CityAgentChat.vue`、`BasketPlanning.vue`、`TravelServiceCards.vue` | 共用结果与类型化事件；已有组件保留渲染，业务总控回到后端 |

旧接口先保留并委托新服务。通过契约与调用方核对后再删除废弃逻辑，不能一次删光V2兼容层。HTTP路径多个本身不是问题，同一业务决策有多个实现才需要消除。

## 10. 实施顺序与验收

| 阶段 | 本阶段成果 | 通过后再推进 |
| --- | --- | --- |
| M0 查询能力契约 | 定义逻辑能力、适配器接口、结果证据与错误协议；列出已有和预留能力 | 无凭据能力不声明可用；注册项无密钥明文；已有接口可映射契约 |
| M1 语义与动作边界 | 一个意图协议，正常问答到达模型；查询与修改分动作校验；酒店查询退出关键词旁路 | 问能力/实际搜索/否定/引用/教程/混合请求回归；只读0业务写入，未知不能默认modify |
| M2 需求与上下文 | 所有入口使用同一需求归并服务，模型看见有效酒店/交通/预算条件和执行摘要 | 多轮、刷新、切旅行、冲突、过期、导出删除；同一字段权威来源唯一 |
| M3 注册表与后端统一编排 | 接入模块内Provider注册表和逻辑查询计划；删除planning前端接力，复用同一exploration/engine与结果协议 | 同能力替换API不改Agent/engine；文本和表单结论一致；故障隔离、旧接口契约及下述扩展验收通过 |
| M4 真实有限链 | 使用已核验有限地点/入口/营业/目标日场次与交通，验证查询→正式预览→确认→途中修改 | 真实Provider与Mock分别报告；正式事实缺失时保持blocked而非换成演示 |
| 后续 多日与深度资料 | 单独扩展住宿跨日依赖、房型权限、评价和精确费用 | 有对应真实数据、权限与独立业务验收后才开放承诺 |

验收不能只看单元测试数：需要中文改写与多轮场景，包括“吗”结尾、间接请求、否定、引用、改价但保留硬要求、概念+查询、同名酒店、接口故障、候选过期、并发修改、关闭留存与删除、原路线进度保护。不能为让聊天顺畅而取消确认、允许无证据事实或漏掉硬约束。

Provider 扩展另验收：配置优先且可用的FlyAI被选择；超时或限流时在预算内尝试已授权备用；无备用时报告单项失败；未授权/禁用Provider零调用；空结果不伪报故障；旧版本迟到结果不覆盖；多来源冲突、不同房型/日期和证据降级明确保留；增加一个测试适配器只改注册配置和适配器，不改Agent协议与engine。Mock验证隔离与协议，真实API另验证权限、字段与时效，两者分别报告。

分别量测语义请求是否执行正确、模型/工具次数、端到端耗时、澄清轮数、用户重复填写、状态变化及硬约束覆盖；不以Mock推断真实模型理解准确率，不给未测的延迟与成功率写保证。

本轮已落地 M0 契约与 M3 的第一批代码：`city/providers/` 提供逻辑能力、适配器、注册、授权状态、备用尝试和 `provider_trace`；旅行服务的酒店、停车、餐饮查询已通过注册表调用现有 FlyAI/高德适配器；前端不再把 Provider 名称写死。天气适配器仍明确保持未绑定状态，正式规划编排、语义统一和真实多 Provider 备用链仍按上表继续推进。未新增真实 Provider 调用，未改写运行库事实或完成度。
