# 汴梁游记产品需求基准

版本：v2.0，2026-10-20。依据用户本轮提供的[产品思路说明](reference/Bianliang_Project_Overview.pdf)和[景区地图产品决策](reference/Bianliang_Park_Map_Strategy.pdf)修订。本文定义新的开发目标，不表示这些目标已经实现。变更依据、代码现状和开发顺序见 [DEVELOPMENT_DIRECTION.md](DEVELOPMENT_DIRECTION.md)。

2026-10-21数据执行补充：用户提供的[城市旅游数据清单](reference/bianliang_data_guide_20261021.pdf)落实为[DATA_REQUIREMENTS.md](DATA_REQUIREMENTS.md)。按完整行程补数，明确菜品—商家供应证据、节目—场次—舞台关联及城市交通按需查询；原采集包为候选来源，不是城市行程验收成果。

## 产品定位与核心问题

汴梁游记面向开封自由行游客，将景点、演出、美食、休息和城市交通组织成一份可以执行、可以途中修改的行程。目标是减少规划负担、无效折返和错过重要体验，让游客按照自己的兴趣和体力游玩。

万岁山武侠城、清明上河园是重点示范场景。产品按城市级行程设计，首版以有限且经过核验的地点完成闭环，不要求覆盖全城，也不要求一天游完两个景区。

产品仍为手机端优先的 Web 应用。原先的“景区内部客流分析是核心研究”“单景区路线演示即可验收”不再作为本期主线。实时客流、精确避堵和排队预测转为有数据、有验证后再加入的增强能力。

典型任务：游客下午到清明上河园，希望看指定演出、吃开封小吃、晚上逛一处城市地点，节奏轻松。系统核对日期、场次、地点、交通和用餐条件，展示整段安排；游客中途休息或跳过一站后，剩余行程仍连续。

## V1 最小范围与交付边界

以下数量和限制是为落地制定的首版工程范围，不是两份来源文档的原文指标：

- 单人或共同行动的一组游客、开封市内、单日行程；同一时刻只执行一个活动。跨日、多团分流留待后续。
- 至少跑通“一个重点景区的已核验局部路线及有效演出 → 一处有明确地址的餐饮地点 → 一处城市游览或夜游地点”，包含园内外转场、返程终点和一次途中修改。
- 两个重点景区都在产品范围内；逐个按数据条件开放深度规划。未通过数据核验的景区保留基础查询和示意展示，不算已完成深度规划。
- 美食是 V1 核心。菜品名称用于表达兴趣；进入可执行行程的必须是可定位、核对营业信息的商户或餐饮地点。用餐时间计入预算，不能只换一组图片。
- 至少一种交通方式在选定范围内有可复核的时间依据。优先打通步行；需要其他方式的任务必须有相应服务或经核验的人工数据，不能用步行时间代替。
- 途中修改以明确的当前地点和时间为起点。V1 可由游客选“我在这里”确认已知地点，不以持续 GPS 定位为前提。

真实路网暂缺时，可以交付标明性质的示意导览和内部算法演示，但不能据此宣布正式 V1 的真实跨场景闭环已验收。缺少客流不会阻塞 V1；缺少必需道路、场次或转场时间会限制相应行程的可执行性。

## 必做能力

| 能力 | 游客可以完成什么 | 验收要求 |
| --- | --- | --- |
| 统一选择与偏好 | 点选景点、场次、美食、休息和城市地点，也可输入自然语言 | 点选路径独立可用；未知地点需匹配确认 |
| 城市级联合规划 | 在同一份行程中安排景区、餐饮、城市游览和交通 | 转场与进出园耗时计入总预算；任何必选项不能被静默删除 |
| 演出衔接 | 看见场次、预计到达、提前到场要求和时间余量 | 日期、持续时间、地点及路径依据完整；不能把缓冲称为排队预测 |
| 行中服务 | 看见下一站、怎么走、预计耗时与需要做的动作 | 地图与行程卡引用同一版本；过期结果有提示 |
| 手动修改与重规划 | 加餐、休息、删站、跳过或调整顺序 | 从当前确认的起点重算剩余行程，保留已完成记录和硬性目标 |
| 行程连续性 | 从园内切到园外、切换地图或返回应用 | 同一城市行程保留进度；不要求重新填写全部需求 |
| 数据不足处理 | 看见明确的待确认项并继续可用操作 | 未知不填零；条件不足不显示“保证能赶上” |

拖动排序不是首版唯一操作方式，可先提供上移、下移及明确的修改按钮，避免手机拖动误触。顺序改变后仍需重新检查时间和道路。

## 输入与输出

必需输入为游玩日期、开始时间、可用时长或结束时间、起点、终点或返程要求，以及至少一个目标。缺项直接补问或用控件补齐；不能擅自假定“下午”为具体时刻。

偏好包括必去地点、必看场次、想吃的菜品或指定商户、步行负担、交通方式、吃饭与休息时段。游客明确指定的目标和锁定安排属于硬约束；一般兴趣属于软偏好。若把已锁定目标改为可选，必须由游客明确同意。

输出是一份有版本的城市行程：活动顺序、每段转场、预计到达与离开、演出及到场要求、用餐与休息、下一站、地图或外部导航入口，以及必要的数据状态。关键事实可展开查看来源和核对日期。

“已核实”修饰事实来源与核对状态；交通耗时仍是估计。结果应分别标记可行性判断和证据状态，不把有来源的时间估计写成确定到达保证。

## 时间判断与修改规则

对演出，先确定最晚到场时间：取已核验的停止入场时刻与“开演时间减提前到场缓冲”中更早者。预计到达晚于该时刻即存在冲突。缓冲是规划参数或场地方要求，不是现场队列测量。

前一场的结束时间、步行或交通时间、进出园转换、用餐、休息、已知等待都要计入。缺少演出结束时间时，不能默认零时长；可以保留为待确认场次，但不能认证整段衔接可行。

无可行方案时，说明冲突的目标与时间，给出可选择的调整。保留上次有效路线；旧路线若已受取消或过期事实影响，应标记失效部分，不能继续显示为有效。

自然语言先提出变更候选，再由游客确认；明确的按钮操作可以直接表达修改意图，系统计算通过后提交。删除必看场次、放宽锁定目标或改动已确认的重要安排，需要展示影响并确认。规则详见 [PLANNING_WORKFLOW.md](PLANNING_WORKFLOW.md)。

## 地图与交互

采用“宋风浅立体”的视觉方向，以道路、位置和关键时间的可读性为前提。这是新设计要求，不是对现有地图已经达标的声明。

- 探索时突出地点、节目和餐饮；执行时突出当前位置或手动起点、下一站和路线；赶演出时突出目的地、最晚到场与时间余量。
- 城市道路优先使用成熟地图服务；园内路线只在核验过的可通行图内计算。两种地图共用同一行程状态。
- 未核验的地图标“示意图”；示意坐标不叠加成真实定位，未连通道路不补直线当路线。
- 无可靠定位时允许手动确认地点；低精度或过期位置必须重新确认。位置权限被拒绝后，基础规划仍可使用。
- 前台只在临近演出、计划冲突、可靠变更或用户主动操作时提醒；V1 不承诺网页关闭后的持续后台提醒或自动发现取消。
- 继续保持手机横向卡片、简洁操作和必要说明；不恢复宣传长文、工程控件或独立客流页面。

原先“美食卡片只做选择反馈”升级为加入行程；“需求只能通过助手收集”升级为地图、卡片、行程编辑与助手共用同一结构化需求。全市美食可以加入城市行程，但不能伪称位于某个景区内部。

## 数据要求和降级

| 数据缺口 | 允许行为 | 不允许的完成声明 |
| --- | --- | --- |
| 无可靠客流 | 普通行程规划；用户主动查询时说明未知 | 当前畅通、精确避堵、排队几分钟 |
| 无园内可靠路网 | 已核实目的地查询、示意展示、外部导览入口 | 精确园内导航、可信步行到场结论 |
| 无目标日期场次或结束时间 | 展示节目介绍或待确认安排，提示补查 | 已安排完整观看且能接下一场 |
| 无商户位置或营业依据 | 保留菜品兴趣或候选地点，等待核对 | 已安排可执行用餐 |
| 无城市交通估时 | 保留地点顺序和外部导航入口，标记待核算 | 跳转地图就等于内部完成全程时间校验 |
| 进出园或再次入园规则未知 | 避免自动设计离园后再入园；保留核对项 | 默认可不限次进出 |

采集资料、已核验可用资料和运行库是三个不同状态。详见 [DATA_SOURCES.md](DATA_SOURCES.md)。

美食供应关系须有菜单、商家公开确认或现场等可追溯证据，不能仅凭店名/分类推断；街区与单店分开建档。交通数据建设建议达到步行加另一种模式；各模式独立核验，不因首条路线仅需步行而声称其他模式已接通。首批建议数量及复核频率见DATA_REQUIREMENTS，不构成现有实现和工期承诺。

## 版本路线与排期

V1 完成城市级闭环，包括基础手动行中修改和当前行程状态。V2 增强自然语言、多轮修改、可信变更接入和经授权的长期偏好；已有 M7 能力可以复用，无需为了版本编号拆掉。V3 扩大真实场景，并按数据质量增强拥挤与道路状态。

先完成园内基础导览和时间判断，再打通城市衔接；这两个实施步骤都属于正式 V1。原“10 天”保留为历史约束，不自动变成扩大范围后的交付承诺。新的冲刺安排必须从数据准备度和剩余工作估算；不得通过删掉美食与城市衔接来宣布 V1 完成。

## 验收与研究评价

工程验收覆盖统一行程、跨场景时间、重要目标保留、地图一致、修改确认、进度保留、失败恢复、缺数据与外部服务失败等场景。通过软件测试只证明对应软件行为，真实路线和游客效果必须另行验证。

正式 V1 至少需要一条真实、限定范围的跨场景路线现场走查，以及一次中途加餐、休息或跳过后的有效接续；记录道路、日期、实际到达和偏差。不要求用一条路线代表全城。

数据验收另覆盖四类任务：跨景区一日游、两场演出衔接、演出间插入真实美食商家、途中修改剩余行程。每类记录输入、事实版本、期望与实际结果；缺少对应真实数据时记未通过/待核验，不能以模拟任务通过代替现场完成。详见[数据执行基准](DATA_REQUIREMENTS.md)。

研究主问题调整为“统一规划和行中修改能否降低游客规划负担、减少错过重要体验并提高任务完成情况”。对照官方导览、普通地图和美食平台的组合，在相同任务、目标、日期与数据条件下评估规划耗时、按时到场比例、无效绕行、调整耗时、跨场景完成率、操作步骤和满意度。

评价口径、样本记录和完成门槛见 [DEVELOPMENT_DIRECTION.md](DEVELOPMENT_DIRECTION.md)。没有预实验前不承诺改善百分比、统计显著性或创新性结论。客流研究作为独立后续实验，不能以模拟惩罚分下降代替游客体验改善证据。

本期不自建城市导航引擎、摄像头识别、精确排队模型、原生 App 或交易系统。票务和酒店可提供真实外部入口；自动购票、预订及支付不在首版范围。
