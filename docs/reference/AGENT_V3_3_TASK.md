## 四、Kimi API 故障诊断

重点解决上一轮联调中的429问题。

参考 Kimi 官方文档：

https://www.kimi.com/help/kimi-api/api-troubleshooting

官方区分的429类型包括：

- `engine_overloaded_error`
- `rate_limit_reached_error`
- `exceeded_current_quota_error`

不能将所有429统一判断为请求太快。

### 4.1 先确定真实原因

在不泄露敏感信息的前提下记录：

- HTTP 状态码。
- 响应中的 `error.type`。
- 脱敏后的错误摘要。
- 如果存在，记录 `Retry-After`。
- 当前模型。
- 单任务实际供应商请求数。
- 请求间隔与并发情况。
- Token 用量。
- 是否触发 SDK 自动重试。

核验当前 Key 与平台地址的匹配关系，但不要输出 Key、完整认证头或其他凭证。

不要擅自更换模型、切换账户、购买额度或充值。

### 4.2 按错误类型分别处理

**服务拥堵：**

尊重供应商返回的等待要求，降低并发，必要时在测试任务外等待下一轮复验。

**速率限制：**

检查实际的请求频率、并发和 Token 预算，以及是否达到 RPM、TPM、TPD 等限制。

**账户配额不足：**

停止在线验收，并明确报告用户需要在官方控制台处理的账户问题。

**SDK 隐式重试：**

检查是否存在默认自动重试导致真实请求数量放大的问题。

在线评测脚本应对真实供应商请求设置可靠的数量上限，计入任何自动重试。

### 4.3 限流策略

默认保持现有“不对429无限自动重试”的设计。

对于在线评测，应优先采用低并发、受控请求间隔与明确的总调用预算。

不能绕过供应商限制。

若本次确实无法继续调用，结束测试并提供准确的阻塞证据及下次复验条件。

不得把确定性降级结果计入真实 Kimi 成功率。

## 五、真实 ReAct 决策链路验收

这是本次最重要的功能验收。

### 5.1 必须验证模型能够观察工具结果

真实 Kimi 至少需要完成一次包含多步决策的任务：

1. 理解游客需求。
2. 选择当前合法查询工具。
3. 接收工具真实返回的结构化结果。
4. 根据结果选择下一合法行动。
5. 必要时调用其他查询或验证工具。
6. 条件满足后调用规划预览。
7. 返回候选或明确停止原因。

不能将预先写死的固定执行顺序冒充 ReAct。

### 5.2 工具调用严格限制

沿用现有受控 JSON 协议及 Pydantic 校验。

当前尚未验证供应商原生 Function Calling，不要求为了本次验收重写成另一套协议。

模型只能选择服务端提供的合法行动。

实际调用参数、工具身份、旅行权限、任务版本和前置条件均由服务端校验。

不得让模型直接执行 SQL、写入正式行程或伪造运营数据。

### 5.3 提前调用工具问题

重点复验此前发现的错误：

模型在资料尚不充分时，提前请求 `preview_plan`。

需要保证：

- 未完成必要资料验证时，规划预览不可执行。
- 非法工具请求被明确拒绝并记录。
- 如允许参数修正，必须在现有修正预算内。
- 无法恢复时安全停止。
- 不能为让模型通过测试而放宽规划前置条件。

建议增加针对不同工具结果的对照测试。

例如：

同样的用户请求，若候选商家营业条件不同，模型应根据观察结果采取合理的不同后续行动。

只记录有依据的行动变化，不把偶然不同视作正确决策。

## 六、核心在线测试场景

### 场景 A：完整成功路径

用户输入：

“我现在有点饿，想吃灌汤包，最好离我近一点，但下午那场演出千万别错过，你帮我看看怎么安排。”

使用隔离合成数据。

数据中必须包含：

- 已确认城市行程。
- 需要保留的演出场次。
- 有菜品供应依据的餐饮商家。
- 有效营业规则。
- 有效位置。
- 方向性交通数据。
- 足以完成完整规划校验的其他必要事实。

由真实 Kimi 完成多轮行动选择。

最终要求：

- 正确保留必看演出。
- 正确处理步行偏好。
- 不编造交通或营业事实。
- 经过全程规划校验后才产生候选。
- 返回可理解的调整建议。
- 正式行程在用户确认前保持不变。

用户确认作为独立受控操作，在隔离测试库中显式模拟，验证提交和状态更新。

不能将模型生成“我确认了”视为真实用户授权。

### 场景 B：观察结果驱动的策略变化

保持用户输入不变，改变合成工具结果。

例如第一种数据存在符合条件的营业商家，第二种数据中候选商家全部不营业或缺少有效供应证据。

测试 Kimi 是否：

- 改变后续合法查询策略。
- 在必要时选择寻找替代候选。
- 无资料时返回 `needs_data` 或其他明确停止原因。
- 不无限查询相同目标。

需要明确记录实际模型选择和对应工具观察结果。

### 场景 C：模型提前请求非法行动

让测试环境出现可能诱发过早规划的条件。

验证服务端前置门禁仍能阻止调用。

如果模型未纠正，应以受控失败结束，不能伪造可行方案。

### 场景 D：用户取消修改

生成尚未确认的候选后，明确执行取消。

验证正式行程版本、已完成记录及锁定要求不变。

### 场景 E：版本变化

在任务执行过程中模拟另一页面更新正式行程。

后续操作必须检测版本变化。

旧候选不允许直接确认。

### 场景 F：供应商失败

通过模拟客户端测试：

- 429各类错误。
- 401授权错误。
- 请求超时。
- 模型返回不合法 JSON。
- 模型请求重复工具。
- 工具缺少必要运营资料。

这些失败用例不必全部消耗真实 Kimi 配额。

应当通过 Mock 和独立测试完成可靠性验证。
