# 四、Kimi 限流机制设计

参考官方资料：

https://www.kimi.com/help/kimi-api/api-troubleshooting

https://www.kimi.ai/help/kimi-api/api-rate-limits

## 4.1 明确限制范围

Kimi 的限制可能涉及：

- RPM：每分钟请求数。
- TPM：每分钟 Token 数。
- TPD：每日 Token 数。
- 并发请求数。

当前已确认3 RPM，但不能假设其他限制完全不存在。

模型调用前需要考虑这些限制。

可以读取供应商返回的限流响应头，但必须兼容不存在相关响应头的情况。

用户目前没有授权更换账号、充值、升级套餐或增加付费资源。

因此不要擅自进行这些操作。

## 4.2 新增统一请求许可机制

请在现有模型客户端外建立一个最小必要的请求调度层。

职责：

- 对同一服务实例内共享的 Kimi 请求实施速率控制。
- 记录实际请求发起时间。
- 限制并发。
- 计算当前是否允许发送新请求。
- 在额度不可用时返回下一次允许尝试的时间。
- 记录供应商真实429并进入适当冷却。
- 支持任务取消和执行预算到期。

不要简单在业务代码内到处插入 `sleep(20)`。

不要通过无限等待占用 HTTP 请求或工作线程。

现有任务采用 step 推进机制，优先复用这种方式。

如果当前尚未获得执行许可，应返回明确的等待状态，由调用方在合适时间继续推进。

等待不应消耗工具行动次数，也不能重复执行前一步已经成功的工具。

## 4.3 调度算法选择

请根据实际部署方式选择能够正确执行的限流策略，例如滑动窗口、GCRA 或具有合理突发控制的令牌桶。

注意：

**不能只做到平均每分钟3次，却允许瞬间突发3次后又立即发送第四次。**

本次低频在线验收建议保守串行发送。

可以以约25秒或更长的请求间隔作为初始实验配置，但必须尊重供应商响应头及实际限速窗口。

这个间隔只是试验参数，不是官方保证不会429的阈值。

如果其他程序也在消耗同一组织额度，本地限流可能仍不足以避免429。

必须保留供应商429的最终处理逻辑。

## 4.4 多进程与多实例问题

请首先确认当前项目的实际部署形态。

如果当前仅运行单进程，可以采用与现有架构匹配的轻量实现。

但必须明确说明：

进程内调度不能保证多个服务进程、不同设备或其他独立应用之间的组织级限流一致性。

如果当前确实需要跨进程协调，可评估使用已有数据库的原子协调能力或项目已有共享组件。

不要为了本次任务立即强行引入 Redis、消息队列或完整分布式任务平台。

必须避免宣称“已经实现组织级全局限流”，而实际只能管理单个 Python 进程。

未来如要面向多个游客正式部署，应提供清晰的共享调度升级路径。

## 4.5 保持错误分类

必须保留和正确处理：

- `rate_limit_reached_error`
- `engine_overloaded_error`
- `exceeded_current_quota_error`
- 401 / 403 授权问题
- 网络超时
- 不合法模型输出

组织 RPM 限制不允许通过立即重复请求解决。

如果供应商提供有效 `Retry-After`，应尊重其要求。

不得出现“429后立即自动连续重试”的行为。

对于余额或权限问题，直接停止并报告。

例如：

模型正确理解需求并完成数次工具调用，但最终任务没有完成。

必须明确列出未验证的环节。

限流、配额、账户权限等外部因素阻止完成在线任务。

需要列出具体错误类型和下一次复验所需条件。

## FAIL：软件功能错误

例如：

调度器错误放行请求、非法工具执行、错误提交正式路线、重复调用导致重复写入等。
