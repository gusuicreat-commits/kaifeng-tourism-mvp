# 汴梁游记 · 小汴梁 V3 自适应旅游任务智能体设计方案

**版本：V3.0 设计稿｜2026年10月21日**

**项目定位：** 面向开封自由行游客，提供能够理解自然语言、持续掌握旅行状态、主动组织查询并辅助调整行程的城市旅游智能体。

**建设原则：** 在 V2 已有能力上增量升级，不重构已验证的行程规划、记忆和业务权限系统。

---

## 一、项目目标

小汴梁 V3 重点解决三个实际问题。

### 1. 游客不会准确表达需求

游客可能一次说很多要求，中间存在省略、纠正和矛盾。

例如：

“我想去清明上河园，算了，先找个地方吃饭吧，最好近点，不过下午那场演出必须看，晚上也别太晚回去。”

系统应该理解用户最终表达的意愿，同时识别不明确的部分，而不是只抓取“清明上河园”“吃饭”两个关键词。

### 2. 复杂任务需要灵活处理

游客希望系统自己协调多个现实条件。

例如：

“找一家能吃灌汤包的店，吃完还能赶上演出，走路最好别超过十分钟。”

系统应能够根据商家、交通和演出查询结果，选择下一步需要验证的信息。

### 3. 用户不希望 AI 擅自改变计划

即使 AI 找到了更好的安排，也应先说明修改内容，等待游客确认。

**V3 最终目标：让游客能够用自然、甚至不完整的语言提出旅行需求，而小汴梁能够可靠地理解、探索和执行。**

---

## 二、整体架构

保留一个小汴梁智能体，不引入多 Agent。

系统采用六个协作模块。

| 模块 | 主要职责 | 建设方式 |
|---|---|---|
| ① 语言理解 | 识别多意图、指代、纠正、约束和不确定性 | V3.1 升级 |
| ② 城市上下文 | 提供当前行程、进度、偏好和待确认事项 | 复用 V2 |
| ③ 任务路由 | 选择直接查询、固定流程、澄清或 ReAct | V3 新增 |
| ④ 有限 ReAct | 根据工具结果选择后续查询和验证 | V3.2 新增 |
| ⑤ 业务工具 | 查询城市事实、交通、演出，调用规划引擎 | 复用并适配 |
| ⑥ 安全控制 | 权限、校验、确认、版本及审计 | 复用并加强 |

整体执行过程：

**用户输入 → 语言理解 → 城市上下文关联 → 任务模式选择 → 查询或规划工具 → 结果校验 → 回复或等待确认。**

其中只有复杂开放式任务进入 ReAct 循环。

## 三、V3.1：增强自然语言理解

这是第一阶段的开发重点。

### 3.1 从单意图升级为多意图理解

同一句话可能包含多个请求。

例如：

“先找个吃的，最好是灌汤包，下午节目别取消，晚上早点回酒店。”

系统需要同时提取：

- 餐饮搜索需求。
- 菜品偏好。
- 必须保留的演出。
- 提前返程的意向。

不能因为存在多个意图，就只执行其中一个。

但是，如果多个意图涉及正式行程修改，需要统一检查约束，而不是独立执行可能相互冲突的修改。

### 3.2 识别四种约束

**硬约束：** “这场演出一定要看。”

**软偏好：** “最好少走一点。”

**可放弃目标：** “有灌汤包最好，没有也行。”

**尚不明确的信息：** “晚上别太晚回来。”

前三种可以进入结构化需求。

第四种需要结合已有时间约束理解，必要时向游客澄清。

模型不能自行把“别太晚”定义为某个具体的强制返程时间。

### 3.3 理解指代关系

重点支持：

“刚才那家店。”

“那个演出。”

“下一个景点。”

“前面第一个方案。”

“还是算了。”

优先从当前旅行、最近讨论对象和有效候选中解析。

如果存在多个可能对象，必须询问用户。

不能为了避免追问而猜测。

### 3.4 理解反悔与纠正

例如：

“我想下午四点去，算了，还是五点吧。”

系统应理解最终目标是五点，而不是生成两个相互冲突的目标。

但需要区分：

**用户修改了当前聊天中的要求**，和**用户请求修改已经正式确认的行程**。

前者可以更新当前任务意图。

后者必须经过现有行程修改流程。

### 3.5 识别真正需要澄清的问题

不能因为一句话有少量模糊信息，就不断追问用户。

建议遵循：

- 不影响正确性的问题，可以使用明确的默认偏好。
- 可以通过现有行程确定的对象，直接读取。
- 可以通过查询可靠事实解决的问题，优先查询。
- 涉及重要取舍、无法确定对象或硬约束冲突的问题，询问用户。

**V3.1 的验收结果应是一份经过校验的结构化旅行意图，而不是直接修改后的行程。**

## 四、任务路由：决定什么时候使用 ReAct

建立统一执行决策层。

### 模式 A：直接查询

适用：

“下一站去哪？”

“今天还有几个景点？”

直接调用当前城市状态查询接口。

### 模式 B：固定工作流

适用：

“把午饭改到下午一点。”

由 Kimi 解析结构化要求，再通过现有确定性规划流程生成预览。

### 模式 C：澄清

适用：

“帮我把刚才那个取消了。”

但当前可能指向两场不同的演出。

系统先明确对象，不进入工具循环。

### 模式 D：有限 ReAct

适用：

“附近找个适合吃饭的地方，别走太远，还要赶上下午的演出。”

允许模型根据查询结果决定下一步操作。

**路由的判断依据是任务路径是否需要动态变化，而不是句子长短或意图数量。**

复杂自然语言可以只需要一次解析；简单表达也可能涉及需要探索的复杂任务。

## 五、V3.2：有限 ReAct 执行器

### 5.1 第一版重点场景

第一版先选择一个代表性任务：

**特色餐饮搜索 + 演出保护 + 交通验证。**

主要原因：

这个任务需要同时考虑多种城市数据，查询结果会影响下一步行动，而且能够直接体现游客价值。

暂不开放通用互联网自主任务执行。

### 5.2 执行过程

假设游客说：

“想吃灌汤包，不要走太远，下午演出不能错过。”

系统应：

**第一步：理解用户要求。**

确认菜品偏好、步行限制、演出约束。

**第二步：读取城市上下文。**

确定本次行程、指定演出和有效当前位置。

**第三步：查询餐饮候选。**

寻找具有可靠菜品供应依据的商家。

**第四步：观察查询结果。**

若没有符合条件的商家，模型可尝试改变允许放宽的搜索条件，例如寻找相近类别的特色美食。

但不能擅自放宽明确的硬约束。

**第五步：检查交通与演出。**

通过现有工具验证是否能够在指定时间内完成就餐并赶上演出。

**第六步：根据结果采取行动。**

如果条件满足，返回候选安排。

如果存在可调整的路线冲突，调用现有规划引擎生成预览。

如果关键数据缺失，明确告知。

如果必须在两个硬约束之间取舍，询问游客。

**第七步：停止执行。**

返回有依据的结果，或进入等待用户确认状态。

不得无限循环。

### 5.3 ReAct 的工具范围

第一版只开放适合旅游任务的受控工具：

| 工具类型 | 允许的操作 |
|---|---|
| 行程查询 | 获取当前正式行程、下一站和版本 |
| 地点查询 | 查询景点及商家候选 |
| 演出查询 | 查询节目、场次和有效时间 |
| 交通查询 | 获取已有可靠路线和耗时信息 |
| 状态查询 | 读取已完成活动、位置和锁定目标 |
| 规划预览 | 调用 OR-Tools 生成候选 |
| 差异比较 | 解释候选相对正式行程的变化 |

工具接口优先复用 V2 已有实现。

不允许 ReAct 直接执行数据库写入，也不允许绕过业务服务调用正式路线提交。

正式确认由独立受控流程处理。

### 5.4 执行控制

建议首版试验配置：

- 单次复杂任务最多4个工具行动。
- 设置模型调用、工具调用和总时间预算。
- 重复无进展的查询自动停止。
- 对参数错误允许有限修正。
- 对权限错误、数据缺失和业务硬约束冲突不进行无意义重试。
- 正式行程版本变化时停止旧候选操作。
- 用户取消任务后停止后续工具调用。

这些参数需要通过实际 Kimi 在线测试调整，不视为已经验证的最佳值。

执行器必须知道什么时候成功、什么时候失败，以及什么时候应该询问用户。

## 六、城市记忆与任务状态协作

V3 不新增独立的长期记忆系统。

继续复用 V2 已有城市上下文服务。

但需要把三类信息严格分开。

| 信息 | 保存和使用方式 |
|---|---|
| 正式旅行状态 | 使用已有数据库，作为业务事实依据 |
| 当前对话与本次偏好 | 按既有会话留存规则读取和管理 |
| ReAct 临时探索过程 | 仅用于当前任务控制和必要的短期恢复 |

例如：

ReAct 搜索了三家餐厅，只找到一家可能合适。

这三次工具查询属于任务过程。

只有游客明确选择并确认之后，相关安排才能进入正式行程。

系统不需要把所有失败的搜索都转化成长期用户记忆。

每次执行前读取必要版本状态；执行过程中如正式路线发生变化，应重新验证候选是否适用。

## 七、错误处理与安全设计

### 7.1 数据真实性

没有可靠商家数据时，不得编造商家。

没有经过核实的演出信息时，不得声称场次有效。

交通信息缺失时，不得凭语言模型估算出一条“确定可以赶上”的路线。

### 7.2 权限和行程保护

沿用 V2 的 M7 权限机制、路线版本、候选确认、事务回滚和数据留存规则。

已经完成的活动、锁定的演出以及其他硬约束继续受到保护。

### 7.3 工具结果不能变成系统指令

商家简介、景点资料、网页内容和其他外部数据，属于查询信息。

即使其中包含“忽略之前规则”等内容，也不能改变 Agent 的权限与执行约束。

### 7.4 输出必须有依据

对实际查询得到的事实，保留来源和更新时间。

对由模型提出、尚未经过规划校验的建议，不能描述成已确认可行的正式安排。

### 7.5 运行日志

记录必要的：

- 任务类型。
- 工具调用及参数摘要。
- 查询结果状态。
- 业务依据引用。
- 重要错误。
- 最终停止原因。
- 耗时与成本。

避免保存模型不必要的完整内部推理文本，延续现有隐私与删除规则。

## 八、游客端交互设计

前端继续采用现有宋韵淡雅风格，不需要为了 Agent 能力加入复杂技术页面。

用户只应感知到三个阶段。

### 1. 理解需求

小汴梁可以简要复述重要要求：

“你希望先吃点东西，同时保留下午的演出，我会按少走路的偏好寻找安排。”

只有必要时才追问。

### 2. 正在处理

对于复杂任务，展示简洁状态：

“正在查找合适商家。”

“正在核对演出时间。”

“正在验证行程安排。”

不展示完整内部推理。

### 3. 反馈结果

结果应尽量包含：

- 找到了什么。
- 为什么适合。
- 哪些条件得到满足。
- 哪些信息尚未核实。
- 是否影响现有行程。
- 需要用户采取什么行动。

如果涉及路线修改，展示变化并提供确认或取消操作。

用户取消探索任务时，不应导致正式行程被修改。

首轮优先完成后端的状态契约，前端只做必要适配，不重构正在并行开发的页面。

## 九、开发阶段划分

### 阶段0：代码与接口审计

检查 V2 已有 Kimi 接入、语言解析、城市上下文、业务服务、规划工具及前端契约。

确认当前真实 Kimi API 是否已完成在线调用测试，以及是否具备所需的结构化工具调用支持。

记录当前基线，不修改无关模块。

### 阶段1：V3.1 自然语言理解升级

完成多意图识别、硬软约束分类、指代消解、纠正识别和澄清策略。

暂时继续通过 V2 工作流执行任务。

**独立验收 V3.1，不以 ReAct 是否完成作为判断标准。**

### 阶段2：V3.2 有限 ReAct 开发

建立受控执行器、动态工具选择、工具结果回传、停止控制与失败降级。

先在合成旅游数据下开发，并使用真实 Kimi 进行在线联调。

### 阶段3：复杂旅游任务集成

优先完成“餐饮 + 演出 + 交通”场景。

将工具结果与现有城市规划引擎连接。

保证正式路线修改仍然采用预览和确认流程。

### 阶段4：前端接入

把新的语言理解、任务状态和候选结果接入小汴梁聊天页面。

同步行程与地图页面的正式状态。

### 阶段5：真实业务与用户测试

接入已核实的真实开封商家、演出和交通资料。

观察真实 Kimi 多轮任务表现。

完成有限实际路线走查和用户体验测试。

## 十、验收与实验方案

采用三组对照方案。

| 实验组 | 方案 |
|---|---|
| A | 当前 V2：意图识别 + 固定工作流 |
| B | V3.1：增强语言理解 + 固定工作流 |
| C | V3.2：增强语言理解 + 有限 ReAct |

### 测试语料

首轮准备80～100条真实游客风格任务，覆盖：

- 模糊表达。
- 一句话多个意图。
- 口语化纠正。
- 跨轮指代。
- 自相矛盾的要求。
- 临时改变计划。
- 多条件地点搜索。
- 演出和餐饮协调。
- 外部数据缺失。
- 工具失败和版本变化。

测试样本应包括人工标注的正确意图、必要约束、预期工具行为和可接受的停止状态。

不能把仅能依赖真实运营数据回答的任务，直接用合成数据结果评价为真实业务成功。

### 评价指标

重点测量：

| 评价方向 | 指标 |
|---|---|
| 理解质量 | 多意图识别准确率、硬约束保留率 |
| 对话体验 | 指代解析成功率、重复澄清次数 |
| 任务效果 | 可验证任务完成率、有效候选率 |
| Agent 控制 | 错误工具调用、重复调用、停止原因 |
| 规划可靠性 | 硬约束通过率、未经确认的正式变更次数 |
| 工程成本 | 响应时间、Kimi Token 与调用费用 |

对 A、B、C 使用相同的输入、已知事实和业务目标。

同时单独统计模拟工具测试与真实 Kimi 在线测试。

**安全验收红线：未经用户有效确认而改变正式行程的次数为零。**

如果 C 相较 B 没有明显提升复杂任务成功率，却显著提高延迟和成本，应缩小 ReAct 的触发范围。

- 对照 V2 的效果分析。

### V3.2 交付

- 有限 ReAct 执行器。
- 任务路由机制。
- 受控工具注册与调用。
- 循环预算、重复检测和停止机制。
- 与城市上下文及规划引擎的集成。
- 复杂旅游任务测试与评测报告。
- 可供前端消费的任务进度和结果状态。

最终报告应清楚区分：

已实现、已验证、仅在合成资料中验证、真实模型已
