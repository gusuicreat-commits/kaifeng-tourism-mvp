## 实际架构

保留单个助手，不新增 Agent 框架、向量库或长期记忆。

1. `city.agent.understand` 把当前文本解析为 `travel-intent/3.2`。每个动作和约束有原文 `quote`；同轮可有多个有界子请求，服务端逐项校验引用、时间、步行秒数。明确的规则约束不能被模型删除或降级。
2. 复用 `city.assistant.context`，从正式城市状态、路线、进度、位置、待确认事项及事实快照构造上下文。聊天只能提供指代和未确认意愿。
3. 路由到 `direct`、`workflow`、`clarify`、`react`、专用只读分支或 `compound`。路由根据是否需要探索决定，不根据句子长短。
4. `city.agent.service` 逐步执行。真实模型通过受限 JSON 选择下一行动，服务端按当前观察结果列出 `eligible_actions`，再次验证参数和前置条件。工具内容不能授权或提交。
5. `toolbelt` 复用事实、交通与规划服务。所有完整方案仍由同一 OR-Tools 求解器和独立校验器核验；Agent 工具表中没有正式提交工具。
6. 游客确认调用 V2 `/assistant/confirm`，复用版本、事实指纹、时效、属主、独立校验及事务提交。

没有验证供应商原生 function calling；当前使用已真实联调的 JSON 输出协议，Pydantic 校验后由服务端选择工具。不是模型直接执行函数或 SQL。

## V3.1 理解与执行适配

结构化输出包括动作数组、约束数组、纠正及不明确事项。约束涵盖菜品、保留演出、步行秒数、返程截止、用餐时刻、游览时刻、优化偏好和节奏。未明确的“晚上别太晚”不会被转成具体时间；“四点，算了还是五点”只保留最终时刻。局部反悔不会删除此前无关的硬约束。

同一句中的查询和修改分别处理：查询结果放在 `answers`，修改仍统一生成候选，不能独立提交互相冲突的修改。不能解析或不能可靠消歧的活动，返回澄清；首版不承诺任意开放式语言都能精确落地。

2026-10-24 R2：`conversation`、只读查询、旅行服务候选和一个规划提案可在同一轮输出，服务端以 `compound.items` 返回每个子请求的状态。查询候选只写服务工作区，规划仍返回预览/提案，正式路线确认接口不变；非法子请求不会触发其他分支的Provider调用。

待澄清意愿复用 `city_proposals`，操作名为 `assistant_v3_intent`，15 分钟失效。后续回答会合并到同旅行、同版本且有效的意愿。V2 和城市状态确认入口都拒绝把此类意愿直接当作正式修改提交。普通只读查询不会覆盖这些意愿。

V2 接口继续保留，新能力通过 `/agent` 显式启用。无模型时语言理解走有限规则，复杂任务执行器使用确定性降级；此时即使路由名为 `react`，也不能把其结果当作真实模型动态选择的证据。

## 有限探索与工具

开放行动只有：

- `search_dining`：查询服务端许可、有效的餐饮地点、营业规则、商家及菜品供应证据；不能根据店名推断菜单。
- `query_shows`：读取当前旅行相关场次，核对日期、开始/结束及有效性。
- `verify_travel`：核对当前手动位置到餐饮、餐饮到下一保护演出的方向交通、用餐时段、入场截止与步行限制。
- `preview_plan`：调用现有首次/剩余行程引擎，完整核对所有目标、后续演出与返程，再展示差异。
- `finish` / `clarify`：停止探索或要求用户取舍。

每一步只把当前合法行动交给模型。没有有效商家不能选该商家核交通；没有演出资料不能验证衔接；没有匹配的交通核验不能生成餐饮候选预览。模型提前请求预览会被拒绝，最多一次参数修正，随后停止。

只有明确为软偏好或可放弃的菜品要求可以放宽搜索；硬要求不能放宽。额外搜索仍消耗行动预算，预算不足时返回未完成，不伪装成功。当前餐饮工具优先处理一次待调整用餐，多次用餐要求先消歧。

交通核验只证明“当前地点—餐饮—下一保护演出”的局部衔接；最终 `preview_plan` 再检查全程，包括其他必选目标和返程。现有用餐时间窗不会因为选商家而丢失。默认用餐 2700 秒、演出缓冲及确认缓冲均为规划参数，不是现场排队或实测保证。

明确的硬步行上限新增为引擎 `Requirements.max_walking_seconds`，表示本次规划区间全部步行段的保守秒数之和；求解器约束及确认时独立校验均覆盖。它不是单段上限，也不修改已执行历史。如果游客表达的上限范围不清，应先澄清。软步行限制只影响偏好，结果不保证满足该数值。

## 预算、取消、版本与隐私

默认单任务最多 4 个工具行动、6 次模型请求、45 秒总墙钟时间、1 次参数修正。理解生成上限 1400 token，行动选择每次上限 200 token；每次注入不超过 12000 字符，单次网络超时不超过 12 秒。模型 401/429、网络故障、关键资料缺失和硬冲突不会自动重试。价格缺少已核对快照时不估算人民币费用，记录供应商返回的 token 用量，费用为 `null`。

任务采用 start / step / get / cancel，无后台工作流。每次 step 执行一步，之前及之后重新检查会话、旅行版本、路线版本和事实指纹；同一任务只允许一个步骤运行。页面改变状态、数据修订或时间预算到期后停止。取消后不发起后续工具；计算中晚返回的候选会被消费，不能确认。已发出的模型请求无法保证撤销供应商计费。

临时探索仅保存在当前进程内存，15 分钟后不可恢复，最多 128 份任务、每会话最多 3 份运行任务。重启或切换到另一进程后返回任务不可用，不假称具备跨进程恢复；正式城市状态不受影响。当前部署是单进程适配，分布式部署前须实现共享任务租约/取消与恢复语义。

启用留存时，复用 M7 消息及 `city_receipts` 保存最小审计：工具名、参数摘要、结果状态、来源 ID、停止原因、耗时及 token 用量；不保存模型完整内部推理。导出覆盖这些回执和待确认意愿。关闭留存清除任务、意愿、候选及派生回执内容；关闭时的新任务只保留执行必要的临时数据，完成后清除输入、结构化意愿和观察。会话删除和 TTL 清理同时清理任务。没有新增长期画像或连续 GPS。

## API 与前端

前缀：`/api/city/v1/trips/{trip_id}/agent`。沿用 M7 cookie、同源边界和对象授权。

| 方法/路径 | 契约 |
| --- | --- |
| POST `/understand` | `StartTask`；独立理解、路由与补问，不保存旅行修改 |
| POST `/tasks` | `StartTask`；检查 `expected_version`、`expected_route_version`，创建幂等临时任务 |
| GET `/tasks/{task_id}` | 当前步骤、模式、阶段、受控审计及结果 |
| POST `/tasks/{task_id}/step` | `AdvanceTask`：`request_id` 和 `expected_step`；一步推进，重复请求不会重复工具 |
| POST `/tasks/{task_id}/cancel` | 停止当前任务并使其未提交候选不可确认 |

正式修改继续使用 `/assistant/confirm`，没有自然语言自动确认接口。机器契约见 [city-agent-v3.schema.json](contracts/city-agent-v3.schema.json)。

前端新增 `CityAgentChat.vue` 与 `cityAgentApi.ts`，在 `/assistant?city_trip=...` 或已有当前旅行的 `/assistant?context=trip` 接入。确认后读取服务端最新状态并更新现有 `journey.trip`，返回行程页再读取最新版本。旧 `/assistant` 单景区入口继续可用。未把城市地图改造为全程核验导航，也没有新增虚构路线几何。
