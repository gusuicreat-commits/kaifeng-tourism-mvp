核对日期：2026-10-23。下面的交互规则以 [PRD](PRD.md) 为准；已有代码与验收边界见 [PROJECT_STATUS](PROJECT_STATUS.md)。产品要求不因代码已有分支就自动算通过。

## E13 深度互动偏好进入规划（2026-10-31，待 Claude 验收）

单日 `Constraints` 和 `MultiDayConstraints` 共用 `TripPreferences`，在工作区保存口味、兴趣与不想安排的类别；同类兴趣与排斥互斥，错误提示为中文。深度模式偏好步骤提供可取消的辣度单选及两组类别多选，选择一组时取消另一组同类，已知条件显示标签；快速模式不显示三组控件、不发送 `preferences`。

`exploration.goal_categories` 按目标类型、地点类型及景区父地点判定演出、美食、夜游和景区；单日、多天都在 `_basket_goals` 排除不想安排或辣度超出的非必去素材，兴趣目标重要性增加 2，必去保留并在回复说明。餐馆按关联商家辣度，菜品只有全部供应商都超出接受程度才排除；辣度未知保留，不能据此称不辣。排除项以 `preference_excluded` 排在每套方案 `unscheduled` 最前，前端单日和多天结果显示名称及原因，素材篮本身不删除。偏好不传入求解器，空偏好沿用原规划行为。

验证入口：`backend/tests/test_trip_preferences.py`，前端 mock 在 `frontend/tests/interaction-mode.spec.ts`，真实本地后端的排除、原因、确认闭环追加于 `frontend/tests/full-flow.spec.ts` 末尾的“偏好条件：真实后端”。本轮仅做条件与表单，不改 Agent 或提示词；对话追问和多天助手回复留给 E14，Playwright 由 Claude 验收。

## E10b 素材篮表单的游玩天数（2026-10-31，待 Claude 浏览器验收）

日期后新增天数步骤，默认 1 天，可选或输入 1–3 天；已知条件中的天数标签可返回修改。单日沿用原请求；多天按首日与天数生成连续日期，共用每天时间、起终点、节奏、交通、人数和偏好，预算上限转为全程 `pricing.total_budget_fen`。快速安排补齐基础条件后直接预览，深度互动仍由游客点击生成。前端不构造目标和过夜：素材篮映射与相邻日同端点的过夜衔接由现有预览接口处理，不同端点仍需补齐住宿衔接。

实际规划上限来自 `backend/app/city/engine/models.py` 的 `MultiDayConstraints.days(max_length=3)` 与连续日期范围校验（1–3 天）；`trip_days` 的字段级上限 30 不代表可执行 30 天。复用现有多天方案预览与整套确认，刷新后从工作区进入原有每日条件面板。浏览器用例见 `frontend/tests/interaction-mode.spec.ts`、`frontend/tests/full-flow.spec.ts`，三天合成资料与两天/三天可行性见 `backend/tests/test_full_flow_browser_fixture.py`。

## 当前实现

发现、详情和地图可加入同一旅程素材篮；`journey.ts`、`cityApi.ts`、`explorationApi.ts` 与 `BasketPlanning.vue` 连接服务端需求工作区及城市引擎。小汴梁可理解日期、时段、地点、预算和偏好，并复用结构化条件。城市状态、素材篮、工作区与正式路线各有版本，不能混为一个已提交安排。

预览经独立校验后由游客明确确认，统一进入 `/engine/confirm`。行程页读取正式版本、显示下一站与进度；地图只投影有效版本。正式数据不足时允许保存意向和查询高德参考路线，不能因继续补问就承诺可以生成正式行程。

旧 `planningWorkflow.ts` / `GuidedPlanner.vue` 保留单景区兼容语义，不再代表全部城市流程。首次及剩余规划的接口见 [规划引擎](PLANNING_ENGINE_V1.md)，助手行为见 [V3](CITY_AGENT_V3.md)。真实数据与现场修改仍未验收。

## 新交互原则

游客可以从探索卡片、地图地点、行程卡或助手开始，所有入口共用同一个 CityTrip 草稿。AI 不作为必经步骤；只询问缺失的关键字段，已提供的信息不要求重复填写。

开始与结束时间、当前位置、锁定目标由游客明确表达。点击菜品只记录想吃什么，需匹配核验商户后才能作为路线停留点。点击具体商户可直接加入候选，系统检查营业与时间。

当前行程、待确认修改和已提交路线分别显示，避免用户误以为“已经加入”就必然“已安排成功”。

## 出发前流程

| 步骤 | 必需处理 | 输出或下一步 |
| --- | --- | --- |
| 选择体验 | 收集地点、场次、美食或餐饮、节奏；区分必选与可选 | 统一候选池和锁定目标 |
| 补齐安排 | 日期、开始与结束、起点和返程、交通方式；必要的吃饭休息窗口 | 可校验的城市需求；缺项定位到控件 |
| 匹配事实 | 同名地点消歧、商户定位、节目日期与结束、道路和出入口 | 已核实项及待确认项，不编造 ID |
| 计算与预览 | 城市转场和园内候选联合求解，整段复核 | 时间卡、地图、必选满足情况和冲突 |
| 确认出发 | 游客核对重要安排；服务器按版本保存 | 同一城市行程及 route_version |

不要求为每个可选偏好单独聊天；跳过表示不限该偏好，不表示允许删除已锁定目标。用户若只浏览地点，不强制填写完整行程。

## 行中流程

1. 显示下一活动、预计到达、路线或导航入口。没有可靠位置时提示选择“我在这里”，只列已知地点；不假装已经定位。
2. 游客可标记完成、跳过、加餐、加休息或修改顺序。完成记录不会被重规划清空；跳过与道路禁止通行分开处理。
3. 服务端读取当前时刻、位置锚点、已完成前缀及未完成目标。计算期间保留当前计划，并标示正在计算。
4. 独立复核通过后按版本提交；地图和卡片同时切换到新版本。失败或冲突时说明原因并保留旧状态，已失效部分仍明确标记。
5. 离园、外部导航返回、进入下一景区仅切换当前段和视图，不新建城市行程，也不抹去餐饮与返程。

## 操作与确认规则

| 操作 | 是否额外确认 | 提交条件 |
| --- | --- | --- |
| 查看地点、展开来源、打开导航 | 不需要 | 不修改业务状态 |
| 首次生成行程 | 需求核对后确认一次 | 全部必需信息及路线校验通过 |
| 点击加入可选餐饮、增加休息、调整可选顺序 | 明确按钮可表达意图，不重复询问相同意思 | 预览或即时反馈结果；若影响锁定项转为影响确认 |
| 删除必看场次、放宽锁定目标、改变重要时间 | 需要展示影响并确认 | 用户明确接受变化，重新求解 |
| 自然语言修改 | 需要候选确认 | 候选属于本人、本行程、本版本且未过期 |
| 标记完成 | 明确完成按钮即可 | 活动属于当前行程和有效状态；不能批量改历史 |
| 收到取消或临时变更 | 提示事实并可计算候选；重要目标变更需确认 | 来源可信且有效；不自动用其他活动替代必选目标 |

以上是持续有效的体验规则；实现必须服从服务端确认与提交门禁，不能只在前端省略确认绕过校验。

## 关键异常

| 情况 | 处理 |
| --- | --- |
| 改游玩日期 | 重新核对所有日期敏感事实；失效场次保留为待处理目标，不悄悄删除 |
| 城市行程中添加或切换景区 | 保持同一城市 trip；重算相关转场，已完成部分不动 |
| 餐饮只有菜名或营业不明 | 保留兴趣或待确认候选；不能声称已安排可执行用餐 |
| 位置过期、精度不足或定位拒绝 | 手动确认已知地点；期间不宣布剩余路线有效 |
| 演出冲突、取消或来不及 | 列出冲突与受影响目标，允许改时间、换场次或主动取消 |
| 结束时间缺失或外部交通失败 | 标记待核算；有明确已知冲突仍展示，不用零时长消除问题 |
| 场次或事实在计算后更新 | 提交校验发现版本变化，候选失效并重新计算 |
| 网络断开、求解失败、版本冲突 | 保留最后提交的版本；可恢复或重试，同 request_id 不重复提交 |
| 会话过期或删除 | 停止显示私有缓存；按真实权限恢复或新建，不依赖旧链接认领行程 |

## 任务地图与提醒

探索、执行、赶演出是同一行程的三个视图状态。地图只显示当前任务相关地点；宋风浅立体不得遮挡道路、箭头、按钮和时间。路线可以有流动效果，但无核验数据不能画成真实导航。

赶演出显示最晚到场和时间余量。红色用于时间冲突时必须标明含义，不能与拥挤热力混用。客流未知不在每张卡上重复占位；用户选择避拥挤或主动查询时简短说明即可。

前台提醒根据最新 route_version 计算；跳过、结束、改时间后旧提醒失效。同一事件避免反复打断。网页关闭后的提醒、自动变更推送、持续定位不是 V1 承诺。

## E21 单日必去冲突调整（2026-10-31，待 Claude 验收）

单日预览没有方案时，必去目标的时间窗/场次时段冲突通过 E9 原因规则生成 `conflicts`，外层状态为 `infeasible`；营业时间未知、场次时刻未知或交通资料不足仍保留资料不足行为。合排冲突逐个核算必去目标，区分单独来不及与同排时间不足；单项计算未完成则如实标为待核算。

复用预览已补齐的同一事实与交通快照，按延后结束、提前开始、换日、改为想去的顺序寻找具体方案。先用 prepare 排除仍缺必选窗口的条件；连同单项诊断最多额外求解 5 次，单次不超过原单日时限与 1 秒的较小值，共享 8 秒预算。日期仅尝试后两天且必须有对应日期资料，时间不越过 07:00/22:00；预算耗尽时保留已找到的方案，不声称穷尽所有调整。途中重规划不提供回到过去或换日的选项。

只有实际求解成功才提供带 patch 的条件选项和带可排地点的降级建议；原有单项 relax 授权按钮保留，不承诺它本身一定可行。游客点击时间/日期选项即同意更新表单并重新预览；仍须确认候选才修改正式行程。多个冲突目标共同降级通过原 answer 入口一次授权、原子修改篮中优先级。旧的不带 patch 时间选项仍进入时间编辑。

回归入口：`backend/tests/test_conflict_adjustments.py`；真实本地后端与合成资料的浏览器用例：`frontend/tests/full-flow.spec.ts` 中“冲突调整：真实后端”。本轮不调用真实模型或外部服务，Playwright 由 Claude 验收。
